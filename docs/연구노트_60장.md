### 1장 — 스프링부트 초기 설정 (1/3) — 프로젝트 구조 및 의존성

| | |

**1. 도메인 중심 패키지 구조 설계**

본 과제는 오프라인 독서 클리닉 센터의 운영을 온라인으로 옮기는 것을 목표로 한다. 학생이 센터에 방문해 책을 추천받고, 그 책을 읽은 뒤 다시 방문해 문제를 풀고, 결과에 따라 보상을 받는 일련의 흐름을 시스템으로 구현해야 한다. 따라서 초기 구조 설계 단계에서 가장 중요하게 고려한 것은 "학생의 학습 사이클"과 "센터의 운영 관리"라는 두 축이 코드 상에서 분리되면서도 자연스럽게 맞물리도록 하는 것이었다.

이를 위해 계층 우선(controller/service/repository를 최상위에 두는) 구조 대신 도메인 우선 구조를 채택했다. 최상위 패키지 `com.hohoedu.book_clinic` 아래에 `student`(학생 계정·로그인), `clinic`(추천·문제풀이·보상의 핵심 로직), `book`(도서 카탈로그), `question`(문제은행), `priority`(권장도서 순위), `monitor`(실시간 모니터링), `diary`(독서일지), `reservation`(클리닉 예약), `payment`·`pass`(결제·이용권), `user`(관리자 계정)를 두었다. 각 도메인 내부에서 다시 Controller → Service → Repository 3계층을 반복하는 형태다.

이 구조를 택한 실질적 이유는 이후 실제로 드러났다. 프로젝트 중반에 학생 학습 로직 전체를 폐기하고 재설계하는 결정(14장)이 있었는데, 이때 `clinic` 패키지와 관련 테이블만 정리하면 되었고 도서 카탈로그나 권장도서 순위처럼 이미 검증된 도메인은 손대지 않아도 되었다. 계층 우선 구조였다면 삭제 범위를 특정하기 어려웠을 것이다.

📷 코드 캡쳐: `BookClinicApplication.java` — `@SpringBootApplication` 선언부 및 패키지 트리

공통 관심사는 `_core` 패키지로 분리했다. 언더스코어 접두어를 붙인 것은 IDE 파일 트리에서 항상 최상단에 정렬되도록 하기 위한 의도적 선택이며, 하위에 `config`(설정 빈), `handler`(전역 예외 처리), `auth`(인증 주체), `filter`·`interceptor`(요청 전처리), `constants`(공통 상수), `utils`, `view`(화면 라우팅 전용 컨트롤러), `file`(업로드 유틸)을 배치했다.

**2. 기술 스택 선정 및 의존성 구성**

프레임워크는 Spring Boot를 사용하고, 화면은 Thymeleaf 서버 사이드 렌더링을 기본으로 한다. SPA(React 등)를 쓰지 않은 이유는 관리자 화면이 대부분 목록·폼 위주의 CRUD이고, 학생 화면 역시 단계별 페이지 이동이 명확해 클라이언트 상태 관리의 복잡도를 감수할 이유가 없었기 때문이다. 다만 학생 화면 중 추천 카드 영역과 문제풀이 화면은 동적 갱신이 필요해 해당 부분만 JS `fetch` 기반으로 구성하는 혼합 방식을 취했다.

영속성 계층은 MyBatis 단일 스택으로 결정했다. 본 시스템의 핵심인 도서 추천 로직(16장)은 학생–센터–재고–우선순위 4개 테이블을 조인하면서 조건부 분기가 들어가는 복잡한 쿼리를 필요로 하는데, 이런 쿼리는 JPA로 표현할 때 가독성과 튜닝 가능성이 모두 떨어진다. XML 매퍼에 SQL을 그대로 두면 후임자가 쿼리를 직접 읽고 수정할 수 있다는 인수인계 측면의 이점도 고려했다.

운영 DB는 기존 사내 시스템과의 연속성을 위해 MS SQL Server(`mssql-jdbc`)를 사용한다. 실시간 모니터링 기능(29~35장)을 위해 Firebase Admin SDK를 추가했으며, 이는 관리자 화면이 폴링 없이 학생의 입실·진행 상태를 즉시 반영받도록 하기 위한 것이다.

**3. 멀티 프로파일 및 DB 초기화 전략**

`application-dev.yml`에는 `spring.sql.init.mode: always`를 설정해 애플리케이션이 기동될 때마다 `schema.sql`과 `data.sql`이 자동 실행되도록 했다. 개발 중 스키마가 자주 바뀌는 상황에서 매번 수동으로 DDL을 적용하는 부담을 없애기 위한 조치다. 다만 이 전략은 이후 도서·문제은행 데이터가 수천 행 규모로 커지면서 기동 시간 문제를 유발했고, 테이블별로 리셋 여부를 나누는 방식으로 재조정되었다(9장, 28장).

### 2장 — 스프링부트 초기 설정 (2/3) — 보안 및 예외 처리 설계

| | |
|---|---|
| **제 목** | 스프링부트 초기 설정 (2/3) — 보안 및 예외 처리 설계 |
| **내 용** | 1. 학생/관리자 이원화 인증 정책<br>2. 전역 예외 처리 구조<br>3. HTTP 상태 코드별 예외 클래스 계층 |

**1. 학생/관리자 이원화 인증 정책**

본 시스템은 성격이 전혀 다른 두 종류의 사용자를 동시에 다룬다. 하나는 센터에 방문한 초등학생이 태블릿으로 접속하는 학생 화면이고, 다른 하나는 센터 직원·본사 관리자가 PC로 접속하는 관리자 화면이다. 두 사용자군은 인증 강도, 세션 유지 시간, 접근 가능 경로가 모두 달라야 하므로 `SecurityConfig`에서 경로 기반으로 정책을 이원화했다.

학생 인증은 아이디·비밀번호가 아니라 학생에게 발급된 앱 아이디(appId) 하나만으로 로그인하는 방식이다. 초등 저학년이 사용자이므로 복잡한 자격 증명을 요구할 수 없고, 물리적으로 센터 내부에서만 접속한다는 전제가 있어 보안 요구 수준을 낮출 수 있었다. 반면 관리자 화면은 센터 코드와 권한 등급에 따라 조회 범위가 달라지므로(35장의 센터별 스코핑 참조) 정식 로그인 세션을 요구한다.

📷 코드 캡쳐: `_core/config/SecurityConfig.java` — `SecurityFilterChain` 빈 정의부

학생용 API인 `/clinic/recommend`, `/clinic/quiz/submit`은 CSRF 예외 및 `permitAll` 대상으로 등록했다. 학생 화면은 PWA로 배포되어 홈 화면에서 독립 실행되는데, 이 환경에서 CSRF 토큰을 세션과 함께 유지하는 것이 브라우저별로 불안정했기 때문이다. 대신 해당 API는 요청 본문의 studentId를 서버에서 실재 여부와 소속 센터까지 검증하도록 하여 무분별한 호출을 차단한다.

**2. 전역 예외 처리 구조**

예외 처리는 `@RestControllerAdvice` 기반의 `GlobalExceptionHandler` 한 곳으로 집중시켰다. 이렇게 한 가장 큰 이유는 학생 화면의 오류 메시지 품질 때문이다. 초등학생이 사용하는 화면에서 "500 Internal Server Error"나 스택트레이스가 노출되면 학생이 상황을 이해할 수 없고 센터 직원이 매번 개입해야 한다. 따라서 모든 예외를 한 지점에서 가로채, 학생이 읽고 다음 행동을 판단할 수 있는 문장으로 변환하도록 했다.

실제로 도서 추천 API에서는 "추천할 수 있는 도서가 더 이상 없습니다", "학생의 소속 센터를 찾을 수 없습니다"처럼 원인을 특정할 수 있는 메시지를 반환하며, 이는 19장의 예외 시나리오 검증에서 실제로 확인되었다. 관리자 화면 예외는 개발자가 원인을 추적할 수 있도록 상대적으로 기술적인 정보를 포함한다.

**3. HTTP 상태 코드별 예외 클래스 계층**

`Exception400`(잘못된 요청), `Exception401`(미인증), `Exception403`(권한 없음), `Exception404`(대상 없음), `Exception405`, `Exception500` 6종을 정의하고, 각 클래스가 응답 바디를 구성하는 `body()`와 상태 코드를 반환하는 `status()`를 구현하도록 통일했다. 서비스 계층에서는 상황에 맞는 예외를 던지기만 하면 응답 형태가 자동으로 일관되게 만들어진다.

이 구조의 실효성은 도서 추천 로직에서 드러났다. 추천 실패는 원인이 여러 가지인데(학생이 존재하지 않음, 센터에 재고가 없음, 파라미터가 비어 있음), 각각을 404·404·400으로 명확히 구분해 던짐으로써 클라이언트가 상황별로 다른 안내를 표시할 수 있게 되었다.

**1. 뷰 컨트롤러 분리 원칙**

화면을 반환하는 컨트롤러와 데이터를 반환하는 REST 컨트롤러를 물리적으로 분리했다. 화면 라우팅은 `_core/view` 패키지의 `AdminViewController`, `StudentViewController`가 전담하고, 도메인 패키지의 컨트롤러는 JSON만 반환한다.

이렇게 나눈 이유는 화면 구성이 개발 과정에서 가장 자주 바뀌는 부분이기 때문이다. 관리자 사이드바에 화면이 하나 추가될 때마다 도메인 컨트롤러를 건드리는 대신 뷰 컨트롤러 한 파일만 수정하면 되고, 반대로 API 스펙이 바뀌어도 화면 라우팅은 영향받지 않는다. 관리자 화면 11개가 모두 오픈 필수 범위로 확정되면서(52장 관련) 이 분리는 실제로 유효하게 작동했다.

📷 코드 캡쳐: `_core/view/AdminViewController.java` — 사이드바 화면별 매핑 목록

**2. 파일 업로드 및 정적 자원 처리**

도서 표지 이미지 업로드를 위해 `_core/file`에 저장 유틸을 두었다. 파일명은 업로드 시각 기반으로 재생성하는데, 동일한 표지 파일명을 가진 도서가 여러 건 등록될 때 덮어쓰기가 발생하는 것을 막기 위함이다. 저장된 이미지는 `WebConfig`의 리소스 핸들러를 통해 `/images/**` 경로로 서빙된다.

**3. 공통 상수 관리**

학년 코드와 시간 슬롯처럼 여러 도메인에서 반복 참조되는 값은 `_core/constants`에 모았다. 특히 학년 코드는 `erp_bookstore_code(gubun='S')` 체계를 따라 '01'(초1)부터 '07'(중등)까지 문자열로 관리하는데, 도서 추천의 학년 상향 fallback 로직(16장)에서 이 코드를 숫자로 변환해 증가시키는 연산이 필요하므로 변환 규칙 자체를 상수와 함께 관리하도록 했다.

시간 슬롯('1'~'4', 즉 1~4교시)은 이후 클리닉 예약 테이블과 실시간 모니터링 화면이 동일한 값을 공유해야 하는 제약(32장)이 있어, 초기부터 상수화해 둔 것이 이후 불일치를 예방하는 역할을 했다.

## II. 도메인 모델 및 DB 스키마 설계 (2026-06-24)

### 4장 — 도메인 모델 설계 (1/2) — 학생·센터·도서 엔티티

| | |
|---|---|
| **제 목** | 도메인 모델 설계 (1/2) — 학생·센터·도서 엔티티 |
| **내 용** | 1. 학생·센터 마스터 설계<br>2. 도서 카탈로그 메타데이터 설계<br>3. 센터별 재고 모델 |

**1. 학생·센터 마스터 설계**

학생(`erp_student`)은 소속 센터 코드(`center_code`)와 학년(`grade_key`) 두 값을 필수로 갖는다. 이 두 값이 본 시스템의 거의 모든 조회에 관여하는데, 센터 코드는 "어떤 실물 도서를 빌릴 수 있는가"를, 학년은 "어떤 난이도의 책을 추천받는가"를 결정하기 때문이다.

특히 센터 코드가 중요한 것은 본 시스템이 온라인 콘텐츠 서비스가 아니라 실물 도서 대여를 전제로 한 오프라인 연계 서비스이기 때문이다. 학생이 아무리 특정 도서를 원해도 자기가 다니는 센터에 그 책의 실물이 없으면 추천 대상이 될 수 없다. 이 제약은 이후 추천 알고리즘의 2번 규칙으로 명문화되었다.

**2. 도서 카탈로그 메타데이터 설계**

도서 카탈로그(`erp_bookstore_content`)에는 제목·저자 같은 기본 정보 외에 분류(`content_type`), 장르(`genre`), 수상정보, 교과 수록 정보, 추천기관, 키워드 태그를 컬럼으로 두었다. 이 메타데이터는 두 가지 목적을 갖는다.

첫째는 학생 화면에서 추천 도서의 가치를 설명하기 위한 것이다. "이 책은 ○○상 수상작이며 △△ 교과에 수록되었습니다"라는 정보가 학생과 학부모에게 추천의 신뢰도를 준다. 둘째이자 더 중요한 목적은 추천 알고리즘의 다양성 확보다. 분류와 장르 두 값을 직전 추천 도서와 비교해 동일하면 제외하는 규칙(16장)이 이 컬럼들 위에서 동작하며, 이는 학생이 비슷한 성격의 책만 연속으로 받는 것을 방지한다.

📷 코드 캡쳐: `schema.sql` — `erp_bookstore_content` 테이블 정의(메타데이터 컬럼 포함)

**3. 센터별 재고 모델**

재고는 `erp_bookstore_item`(도서 개별 실물)과 `erp_bookstore_item_center`(센터별 보유 현황)로 나누어 관리한다. 후자에는 총 보유 수량(`total_qty`)과 현재 대여 중인 수량(`loaned_qty`)을 별도 컬럼으로 두고, 대여 가능 재고를 두 값의 차로 계산하는 구조를 택했다.

가용 재고를 직접 컬럼으로 두지 않고 계산하도록 한 것은 데이터 정합성 때문이다. 대여와 반납이 동시에 일어날 때 가용 수량 컬럼을 직접 증감하면 경합 상황에서 값이 틀어질 수 있지만, `loaned_qty`만 조건부로 증가시키고 총량은 고정값으로 두면 "총량을 초과하는 대여"가 SQL 레벨에서 원천 차단된다. 이 설계는 17장의 동시성 방어 로직으로 이어진다.

### 5장 — 도메인 모델 설계 (2/2) — 매퍼 구조 및 계층 규약

| | |
|---|---|
| **제 목** | 도메인 모델 설계 (2/2) — 매퍼 구조 및 계층 규약 |
| **내 용** | 1. 매퍼 XML 분리 규칙<br>2. 계층 간 역할 규약<br>3. DTO 명명 및 배치 규약 |

**1. 매퍼 XML 분리 규칙**

MyBatis 매퍼 XML은 `src/main/resources/mapper/` 아래에 도메인별로 한 파일씩 두고, 각 파일이 동일한 이름의 Repository 인터페이스와 1:1로 대응하도록 규칙을 정했다. `ClinicMapper.xml` ↔ `ClinicRepository.java` 형태다.

파일을 잘게 쪼개지 않고 도메인 단위로 묶은 것은, 하나의 도메인 안에서 여러 쿼리가 같은 조인 구조를 공유하는 경우가 많아 한 파일에서 함께 보는 것이 유지보수에 유리하다고 판단했기 때문이다. 실제로 `ClinicMapper.xml`에는 추천 후보 조회, 대여 처리, 완독 이력 조회가 모두 학생–센터–재고 조인을 공유하고 있다.

**2. 계층 간 역할 규약**

Controller는 요청 파라미터 검증과 응답 변환만 담당하고 비즈니스 판단을 하지 않는다. Service는 트랜잭션 경계이자 도메인 규칙이 위치하는 곳이며, Repository는 SQL 실행만 담당한다.

이 규약을 명시적으로 정한 이유는 도서 추천 로직 때문이다. 추천은 "우선순위 순으로 후보를 훑되, 조건에 맞는 것이 없으면 조건을 완화해 재시도하고, 그래도 없으면 학년을 올려 다시 시도한다"는 다단계 판단을 포함한다. 이 판단을 SQL 안에 넣으면 쿼리가 비대해지고 디버깅이 불가능해지므로, SQL은 "주어진 조건에서 후보 1건 조회"만 담당하고 재시도·완화 판단은 Service의 Java 코드에 두기로 했다. 이 분리 덕분에 이후 규칙 3~5가 실제로 동작하지 않는 상태였음을 코드 리뷰로 발견할 수 있었다(18장).

**3. DTO 명명 및 배치 규약**

요청·응답 객체는 각 도메인의 `_dto` 하위 패키지에 두고 `XxxDTO` 접미사로 통일했다. 엔티티를 화면에 직접 노출하지 않는 원칙을 세웠는데, 특히 문제은행 데이터의 경우 정답(`ans`) 필드가 포함되어 있어 그대로 내려보내면 보안 문제가 되기 때문이다. 이 문제는 실제로 23장에서 부분적으로 해결되었으나 완전히 해소되지는 않아 잔여 과제로 남아 있다.

### 7장 — 문제은행 설계 (2/3) — 기본·심화 문항 구조

| | |
|---|---|
| **제 목** | 문제은행 설계 (2/3) — 기본·심화 문항 구조 |
| **내 용** | 1. 문항 난이도 이원화(qlevel)<br>2. 문항 수와 정답 구조<br>3. 심화 문항의 미완결 상태 |

**1. 문항 난이도 이원화(qlevel)**

문제은행(`erp_bookstore_itempool`)은 도서 1권에 대해 여러 문항을 갖는 구조이며, 각 문항은 난이도 구분자 `qlevel`을 갖는다. '01'은 기본 문항, '02'는 심화 문항이다.

난이도를 두 단계로 나눈 것은 학습 동기 설계와 관련이 있다. 기본 문항을 통과한 학생에게 곧바로 다음 책을 주면 성취가 단발적으로 끝나지만, 심화 문항이라는 선택적 도전 과제를 제공하면 같은 책에서 한 번 더 성취를 경험할 수 있다. 이 구조는 이후 보상 체계 재편(37장)에서 심화 전용 뱃지 2종을 두는 근거가 되었다.

**2. 문항 수와 정답 구조**

기본 문항은 도서당 12문항 또는 15문항으로 구성한다. 각 문항은 문항 번호(`qnum`), 지문, 보기, 정답(`ans`)을 갖는다. 문항 수가 두 가지로 나뉜 것은 도서의 분량과 난이도에 따라 출제 담당자가 조정한 결과이며, 이 때문에 이후 채점 로직에서 합격선을 고정 숫자가 아니라 비율로 일반화할 필요가 생겼다(20장).

📷 코드 캡쳐: `schema.sql` — `erp_bookstore_itempool` 테이블 정의(`qlevel`, `qnum`, `ans` 컬럼)

**3. 심화 문항의 미완결 상태**

심화 문항은 스키마와 화면 흐름은 갖추었으나, 본 연구 기간 중 실제 시드 데이터가 한 건도 등록되지 않았다. 따라서 "심화문제 풀기" 버튼과 라우팅, 문항이 없을 때의 빈 상태 처리("이 책에 등록된 문제가 아직 없어요")까지는 검증했으나 실제 풀이 흐름 전체를 관통하는 테스트는 수행하지 못했다. 이는 콘텐츠 제작 일정에 종속된 사항으로, 데이터 등록 후 재검증이 필요한 항목으로 기록해 둔다.

## IV. 데이터 정비 및 식별자 설계 (2026-07-02 ~ 07-03)

### 9장 — 시딩 데이터 구조 분리 (1/2)

| | |
|---|---|
| **제 목** | 시딩 데이터 구조 분리 (1/2) |
| **내 용** | 1. 기동 시간 문제의 발생<br>2. 리셋 대상과 보존 대상의 분리<br>3. 분리에 따른 제약과 부작용 |

**1. 기동 시간 문제의 발생**

개발 초기에는 `schema.sql`이 모든 테이블을 DROP 후 재생성하고 `data.sql`이 모든 초기 데이터를 삽입하는 단순한 구조였다. 그러나 문제은행 데이터가 5,918행 규모로 늘어나면서 애플리케이션 재기동마다 이 데이터를 전부 다시 삽입하는 시간이 개발 효율을 심각하게 저해하기 시작했다. 개발 도구의 핫 리로드까지 포함하면 하루에도 수십 번 재기동이 발생하는 상황이었다.

**2. 리셋 대상과 보존 대상의 분리**

이에 데이터를 성격에 따라 두 부류로 나누었다. 도서 카탈로그(`content` 계열), 문제은행(`itempool`), 센터 마스터(`erp_center`), 센터별 재고(`item_center`)는 "한 번 넣으면 바뀌지 않는 기준 데이터"로 보고 리셋 대상에서 제외했다. 이들 테이블은 `schema.sql`에서 DROP 구문을 주석 처리하고 `CREATE TABLE`에 존재 여부 가드를 걸어, 최초 1회만 생성되고 이후에는 재기동해도 유지되도록 했다. 해당 데이터는 `data-books.sql`과 `data-itempool.sql`로 분리해 자동 실행 목록에서 빼고, DB 도구로 최초 1회만 수동 실행하는 절차로 전환했다.

반면 학생 계정, 관리자 계정, 뱃지·레벨 정의, 테스트용 데모 데이터는 개발 중 자주 변경되고 초기화가 필요하므로 `data.sql`에 남겨 매 기동 리셋되도록 유지했다.

📷 코드 캡쳐: `schema.sql` — 리셋 제외 테이블의 존재 여부 가드 구문

**3. 분리에 따른 제약과 부작용**

이 분리는 부작용을 동반했다. 첫째, 센터별 재고 테이블이 센터 마스터를 외래 키로 참조하기 때문에, 재고를 리셋 제외하면 센터 마스터도 함께 제외할 수밖에 없었다. 그렇지 않으면 DROP 시 외래 키 제약 위반이 발생한다.

둘째, 재고 테이블이 리셋되지 않는다는 것은 대여 카운터(`loaned_qty`)가 개발 세션을 넘어 계속 누적된다는 뜻이다. 실제로 테스트 중 소진된 도서들이 재고 0 상태로 남아, 추천 결과가 "우선순위 1번 책"이 아니라 "아직 재고가 남은 다음 책"으로 나타나는 현상이 관찰되었고, 이를 로직 버그로 오인해 원인 파악에 시간을 소모한 사례가 있었다. 이 문제는 이후 재고 테이블을 다시 리셋 대상으로 되돌리는 결정(28장)으로 이어졌다.

### 10장 — 도서 식별자(bcode) 설계 변경 (2/2)

| | |
|---|---|
| **제 목** | 도서 식별자(bcode) 설계 변경 (2/2) |
| **내 용** | 1. ISBN 수기 입력 방식의 문제<br>2. 서버 발급 식별자로의 전환<br>3. 전환에 따른 기능 상실과 재검토 필요성 |

**1. ISBN 수기 입력 방식의 문제**

도서 식별자 `bcode`는 초기에 실제 ISBN 바코드 값을 사용했다. 그러나 담당자가 도서 뒷면의 13자리 숫자를 화면에 직접 입력하는 방식이었기 때문에 오타가 빈번했고, 잘못 입력된 식별자가 그대로 저장되는 사례가 누적되었다.

**2. 서버 발급 식별자로의 전환**

이에 식별자를 서버가 자동 발급하는 숫자형 값으로 전환했다. 발급 규칙은 현재 시각의 밀리초 값에 난수 5자리를 결합하는 방식으로, 사실상 충돌하지 않는 고유값을 보장한다. 이 변경으로 수기 입력 자체가 사라져 오타 문제는 완전히 해소되었다.

📷 코드 캡쳐: `BookService.generateNumericBcode()` — 식별자 발급 로직

**3. 전환에 따른 기능 상실과 재검토 필요성**

그러나 이 전환은 ISBN이 제공하던 여러 기능을 함께 잃는 결과를 낳았다. ISBN은 단순한 내부 식별자가 아니라 전 세계적으로 통용되는 도서 표준 식별자이므로, 이를 보유하고 있으면 (1) 동일 도서의 중복 등록을 자동 판별할 수 있고 (2) 실물 도서의 바코드를 스캐너로 읽어 시스템과 연동할 수 있으며 (3) 외부 도서 API를 통해 서지 정보를 자동으로 가져올 수 있고 (4) ISBN-13 체크섬 규칙으로 입력값의 유효성을 자체 검증할 수 있다. 식별자를 임의 발급 값으로 바꾸면서 이 네 가지가 모두 불가능해졌다.

특히 주목할 점은 오타 문제의 본질이 "ISBN이라는 식별자 체계"가 아니라 "수기 입력이라는 입력 방식"에 있었다는 것이다. 바코드 스캔 입력이나 체크섬 검증을 도입했다면 ISBN을 유지하면서도 오타를 막을 수 있었다. 현재 시딩 데이터(`data-items.sql`)는 여전히 실제 ISBN 13자리 값을 사용하고 있어 운영 코드가 생성하는 값과 형식이 불일치하는 상태이며, 이는 ISBN 복원 시 오히려 자연스럽게 해소되는 문제다. 본 사항은 재검토 대상으로 기록해 둔다(54장).

**1. 순위 개념의 도입 배경**

본 시스템에서 도서 추천은 학생의 취향을 학습하는 개인화 알고리즘이 아니라, 교육 전문가가 정한 커리큘럼 순서를 따르는 방식이다. 초등 저학년 독서 교육에서는 읽는 순서 자체가 교육적 의미를 갖기 때문에, 학생마다 다른 순서로 책을 접하는 것보다 검증된 순서를 따르게 하는 편이 낫다고 판단했다.

이에 따라 학년별로 도서에 순위를 부여하는 `erp_bookstore_priority` 테이블을 두고, 추천 알고리즘은 이 순위를 1차 기준으로 삼는다. 개인화 요소는 순위를 훑는 과정에서 재고 여부와 직전 추천 도서와의 유사도로만 반영된다.

**2. 확정본·임시본 이원화 설계**

순위 테이블은 확정본(`priority`)과 편집 중 임시본(`priority_draft`)으로 이원화했다. 관리자가 순위를 조정하는 동안 실서비스 추천 로직이 미완성 순위를 참조하는 것을 막기 위해서다.

📷 코드 캡쳐: `schema.sql` — `erp_bookstore_priority` 및 `priority_draft` 테이블 정의

이 구조에서 관리자는 임시본을 자유롭게 수정하다가 "확정" 조작을 통해 한 번에 확정본으로 반영한다. 순위 조정은 수십 건의 도서 순서를 동시에 바꾸는 작업이므로, 중간 상태가 그대로 서비스에 노출되면 학생이 일시적으로 잘못된 순서의 책을 받게 된다.

**3. 학년별 순위 관리**

순위는 학년(01~07) 단위로 독립적으로 관리된다. 다만 본 연구 기간 중 06(초6), 07(중등) 학년에 대해서는 순위 데이터가 등록되지 않았는데, 이는 해당 학년 대상 콘텐츠가 아직 준비되지 않았기 때문이다. 이 상태에서 해당 학년 학생이 추천을 요청하면 어떻게 동작하는지는 19장에서 별도로 검증하였다.

## VI. 도서 추천 로직 1차 설계 (2026-07-07 ~ 07-08)

### 13장 — 추천 알고리즘 초안 설계

| | |
|---|---|
| **제 목** | 추천 알고리즘 초안 설계 |
| **내 용** | 1. 추천 후보 조회 쿼리 설계<br>2. 로그인 경로 이원화 시도<br>3. 재추천 기능의 구조적 결함 발견 |

**1. 추천 후보 조회 쿼리 설계**

추천의 핵심 쿼리는 "이 학생이 다음에 읽을 책 1권"을 찾는 것이다. 조건은 세 가지다. 학생의 학년에 해당하는 권장도서 순위 목록에 있어야 하고, 학생이 다니는 센터에 대여 가능한 실물 재고가 있어야 하며, 학생이 이미 받은 적 없는 책이어야 한다.

이를 위해 권장도서 순위 테이블을 기준으로 도서 카탈로그, 센터별 재고, 학생의 추천 이력을 조인하는 쿼리를 작성했다. 정렬은 순위 오름차순이며 상위 1건만 취한다. 이 조인 구조는 이후 전면 재설계 과정에서도 그대로 유지되어, 재설계가 알고리즘의 판단 로직에 집중되고 데이터 접근 부분은 재사용될 수 있었다.

📷 코드 캡쳐: `ClinicMapper.xml` — `pickNextContentId` 후보 조회 쿼리

**2. 로그인 경로 이원화 시도**

초기 설계에서는 학생이 센터에 도착했을 때의 상황을 두 가지로 나누어, 출석(새 책을 받으러 옴)과 문제풀이(읽은 책의 문제를 풀러 옴)를 별도 로그인 경로로 구분하려 했다. 학생이 로그인 화면에서 자신의 목적을 선택하면 이후 화면 흐름이 갈라지는 방식이다.

**3. 재추천 기능의 구조적 결함 발견**

여기에 "다른 책 추천" 버튼을 두어 학생이 받은 책이 마음에 들지 않으면 다시 추천받을 수 있도록 했는데, 이 기능에서 심각한 결함이 발견되었다. 재추천이 실행될 때 이전에 추천된 책의 대여를 반납 처리하지 않고 새로운 책을 추가로 대여하는 구조였던 것이다.

그 결과 학생이 재추천을 누를 때마다 센터의 가용 재고가 하나씩 영구히 감소했다. 실물이 실제로 대여된 것이 아님에도 시스템상으로는 대여 중으로 기록되어, 다른 학생이 그 책을 받을 수 없게 되는 상황이다. 이 문제는 단순한 버그 수정으로 해결할 성격이 아니라 "학생이 추천을 거부할 수 있는가"라는 정책 판단을 요구하는 사안이었고, 결국 다음 단계에서 재추천 기능 자체를 제거하는 결정으로 이어졌다(15장).

## VII. 학생 학습 로직 전면 재설계 (2026-07-09)

### 14장 — 재설계 결정의 배경과 범위 확정

| | |
|---|---|
| **제 목** | 재설계 결정의 배경과 범위 확정 |
| **내 용** | 1. 기존 구현의 구조적 문제 진단<br>2. 재설계 범위 결정 — 스키마까지 초기화<br>3. 재설계 후 진행 순서 정의 |

**1. 기존 구현의 구조적 문제 진단**

이 시점까지 레벨·경험치·뱃지·문제풀이 채점을 포함한 학생 학습 로직이 일차적으로 구현되어 있었다. 그러나 실제로 흐름을 처음부터 끝까지 사용해 보니 개별 기능은 동작하는데 전체가 맞물리지 않는 문제가 드러났다.

가장 근본적인 문제는 추천 단계에 있었다. 앞서 발견된 재추천 시 재고 누수(13장) 외에도, 추천 이력이 "학생이 이 책을 받았다"는 사실만 기록할 뿐 "그 책을 다 읽고 문제까지 풀었는가"라는 상태를 갖고 있지 않았다. 그 결과 학생이 책을 완독해도 시스템은 그 사실을 알지 못했고, 다음 책을 추천할 트리거가 존재하지 않았다. 추천–학습–완료–재추천으로 이어져야 할 순환이 첫 바퀴에서 끊긴 셈이다.

보상 체계 역시 문제풀이 결과와 연결되는 지점이 불명확했다. 경험치를 어느 시점에 얼마나 지급하는지, 재도전한 경우 중복 지급을 어떻게 막는지가 설계되지 않은 상태에서 테이블만 존재했다.

**2. 재설계 범위 결정 — 스키마까지 초기화**

부분 수정으로 대응할 경우 기존의 잘못된 전제가 남아 문제가 재발할 것으로 판단하여, 학생 학습 관련 로직을 데이터베이스 스키마 수준까지 전부 초기화하고 처음부터 다시 설계하기로 결정했다. 삭제 대상은 레벨, 경험치 규칙, 캐릭터, 학생 진행 정보, 뱃지, 학생 뱃지 이력, 독서 이력 등 8개 테이블과 이에 대응하는 서비스·컨트롤러·리포지토리 코드 전체였다.

반면 이미 검증이 끝났거나 학습 로직과 무관한 영역은 그대로 보존했다. 학생 명부, 도서 카탈로그, 권장도서 순위, 재고 관련 테이블이 여기 해당한다. 1장에서 도메인 중심 패키지 구조를 택한 것이 이 시점에서 실질적 이점으로 작용했다 — 삭제 범위를 `clinic` 도메인과 관련 테이블로 명확히 특정할 수 있었기 때문이다.

**3. 재설계 후 진행 순서 정의**

재설계는 학생의 실제 경험 순서를 그대로 따라 세 단계로 나누어 진행하기로 했다. 1단계는 책 추천, 2단계는 문제풀이와 채점, 3단계는 결과 산출과 보상 지급이다.

이 순서를 택한 이유는 각 단계가 앞 단계의 산출물을 전제로 하기 때문이다. 추천 이력의 상태 값이 정의되어야 채점 결과를 어디에 기록할지 정할 수 있고, 채점 결과가 있어야 보상 지급 기준을 정할 수 있다. 실제로 1단계 완성 후 2단계를 구현하는 과정에서 1단계에 도달 불가능한 코드가 있었음이 드러났고(18장), 이는 순차 진행이 아니었다면 발견하기 어려웠을 문제였다.

더 중요한 것은 이 선택이 실제로는 불필요했다는 점이다. 학생이 아직 읽지 않은 책을 갖고 있다면 문제를 풀 차례이고, 갖고 있지 않다면 새 책을 받을 차례다. 이는 시스템이 추천 이력을 조회해 스스로 판단할 수 있는 정보이지 사용자에게 물어볼 사항이 아니다. 관련 화면(`student-index.html`)과 분기 파라미터를 모두 삭제했다.

재고 누수를 유발하던 "다른 책 추천" 기능은 반납 처리를 추가해 고치는 대신 기능 자체를 제거하기로 했다. 이는 기술적 판단이 아니라 서비스 정책 판단이었다.

본 시스템의 추천은 교육 전문가가 정한 커리큘럼 순서를 따르는 것이므로(11장), 학생이 순서를 거부하고 다른 책을 요구할 수 있게 하는 것은 커리큘럼의 취지와 상충한다. 또한 실물 도서 대여를 전제로 하는 구조에서 재추천은 필연적으로 반납 처리를 동반해야 하는데, 학생이 실제로 책을 손에 쥐기 전이라면 몰라도 이미 받아간 후라면 시스템만으로 반납을 판단할 수 없다. 정책과 구현 양쪽에서 정당화되지 않는 기능이라고 결론지었다.

### 16장 — 도서 추천 재설계 (2/3) — 추천 규칙 5단계 확정

| | |
|---|---|
| **제 목** | 도서 추천 재설계 (2/3) — 추천 규칙 5단계 확정 |

**1. 규칙 1·2 — 순위와 재고**

추천 알고리즘은 다섯 개의 규칙을 순차적으로 적용하는 구조로 확정했다. 첫 두 규칙은 후보를 결정하는 필수 조건이다.

규칙 1은 권장도서 순위(`sort_order`) 오름차순으로 후보를 훑는 것이다. 앞서 정리했듯 본 시스템의 추천은 교육 커리큘럼을 따르는 방식이므로, 순위가 가장 앞선 미독서 도서가 언제나 1순위 후보가 된다.

규칙 2는 학생 소속 센터에 대여 가능한 실물 재고가 있는 도서만 후보로 인정하는 것이다. 순위상 앞선 책이라도 그 센터에 실물이 없으면 학생이 실제로 가져갈 수 없으므로 건너뛴다. 이 두 규칙만으로 대부분의 추천이 결정된다.

**2. 규칙 3·4 — 유사 도서 회피와 조건 완화**

규칙 3은 다양성 확보를 위한 것이다. 직전에 추천받은 도서와 분류(`content_type`)와 장르(`genre`)가 **모두** 같은 도서는 후보에서 제외한다. 두 값 중 하나만 같은 경우는 제외하지 않는데, 조건을 지나치게 엄격하게 잡으면 후보가 급격히 줄어들어 순위를 무시하고 멀리 떨어진 책으로 건너뛰게 되기 때문이다. 커리큘럼 순서 준수와 다양성 사이의 균형점을 두 값이 모두 일치하는 경우로 잡았다.

규칙 4는 규칙 3의 안전장치다. 유사 도서를 제외한 결과 후보가 하나도 남지 않으면, 제외 조건 없이 처음부터 다시 훑는다. 다양성은 가능하면 확보하되, 그것 때문에 추천 자체가 실패하는 상황은 허용하지 않는다는 우선순위를 코드로 표현한 것이다.

**3. 규칙 5 — 학년 상향 대체**

규칙 5는 학생이 자기 학년의 권장도서를 모두 읽었을 때 적용된다. 이 경우 학년을 한 단계씩 올려가며 상위 학년의 권장도서 목록을 다시 훑는다. 학년 코드를 숫자로 변환해 1씩 증가시키며, 중등에 해당하는 상한(07)까지 시도한 뒤에도 후보가 없으면 추천 불가로 처리한다.

이 규칙은 학습 진도가 빠른 학생을 위한 것이다. 초등 저학년의 경우 학년당 권장도서가 수십 권이므로 1년 안에 모두 읽는 경우는 드물지만, 시스템이 그 상황에서 아무것도 하지 못하고 멈추는 것은 부적절하다고 보았다. 다만 이 규칙이 자주 발동한다면 그것은 해당 학생의 학년 설정 자체를 상향 조정해야 한다는 신호이므로, 운영 관점에서는 예외적 안전장치의 성격을 갖는다.

### 17장 — 도서 추천 재설계 (3/3) — 멱등성과 동시성 처리

| | |
|---|---|
| **제 목** | 도서 추천 재설계 (3/3) — 멱등성과 동시성 처리 |
| **내 용** | 1. 멱등성 확보 — 중복 추천 방지<br>2. 대여 확정과 재고 차감의 결합<br>3. 동시 요청 상황의 방어 |

**1. 멱등성 확보 — 중복 추천 방지**

추천 API는 학생이 메인 화면에 진입할 때마다 자동 호출되므로(15장), 같은 학생이 하루에도 여러 번 이 API를 호출하게 된다. 화면을 새로고침하거나 뒤로 갔다가 돌아오는 것만으로도 호출이 발생한다. 따라서 이 API는 반드시 멱등해야 한다 — 여러 번 호출해도 결과가 첫 호출과 동일해야 한다.

이를 위해 API는 먼저 해당 학생에게 아직 완료되지 않은 추천 이력이 있는지 확인한다. 있으면 새로 추천하지 않고 그 책을 그대로 반환하며, 이때 대여 처리도 다시 하지 않는다. 없을 때만 규칙 1~5를 적용해 새 책을 고르고 대여를 확정한다.

이 멱등 처리는 단순히 중복 호출을 막는 것을 넘어 서비스의 핵심 규칙을 표현한다. "학생은 한 번에 한 권만 진행한다"는 원칙이 이 로직 하나로 강제되며, 별도의 상태 관리 없이도 학생이 책을 반납(문제 풀이 완료)하기 전에는 다음 책을 받을 수 없다.

**2. 대여 확정과 재고 차감의 결합**

새 추천이 확정되는 시점에 추천 이력 기록과 재고 차감이 함께 이루어진다. 두 작업은 하나의 트랜잭션으로 묶여, 이력은 남았는데 재고가 차감되지 않거나 그 반대인 상황을 방지한다.

📷 코드 캡쳐: `ClinicService.recommendBook()` — 멱등 확인 및 대여 확정 분기

**3. 동시 요청 상황의 방어**

같은 학생이 두 대의 기기에서 동시에 로그인하는 등 추천 API가 병렬로 호출되는 상황을 검토했다. 이 경우 두 요청이 모두 "진행 중인 책 없음"으로 판단하고 각자 새 책을 대여하려 시도할 수 있다.

이에 대한 방어는 재고 차감 쿼리 자체에 구현했다. 재고 차감은 무조건적인 UPDATE가 아니라 "현재 대여 수량이 총 보유 수량보다 작을 때만" 갱신하는 조건부 UPDATE이며, 영향받은 행이 0이면 재고 없음으로 판정한다. 두 요청이 동시에 들어와도 DB가 UPDATE를 직렬화하므로 한쪽만 성공하고, 나머지 한쪽은 재고 없음 응답을 받는다. 4장에서 가용 재고를 별도 컬럼으로 두지 않고 계산하도록 설계한 것이 여기서 효과를 발휘했다.

다만 이 방어는 데이터 정합성만 보장할 뿐 사용자 경험 측면에서는 완전하지 않다. 나중에 도착한 요청이 "먼저 성공한 요청의 결과"를 대신 받는 것이 아니라 오류 응답을 받기 때문이다. 발생 빈도가 낮고 정합성에는 문제가 없어 개선 우선순위는 낮게 두었다(57장).

### 18장 — 추천 로직 검증 (1/2) — 도달 불가 코드의 발견

| | |

**1. 기본 시나리오 검증 결과**

추천 로직 구현 후 실제 데이터로 전수 검증을 수행했다. 신규 학생의 첫 추천에서 권장도서 순위 1번 도서가 정확히 선택되고 추천 이력·대여 이력·재고 카운터가 모두 일관되게 반영되는 것을 확인했다. 동일 학생이 API를 재호출했을 때 완전히 같은 책이 반환되고 중복 기록이 생기지 않는 것으로 멱등성도 검증되었다.

재고가 소진된 경우의 동작도 확인했다. 순위 1번 도서의 재고를 인위적으로 0으로 만든 뒤 추천을 요청하니 2번 도서로 정확히 넘어갔다.

**2. 규칙 3~5가 실행되지 않는 문제 발견**

그러나 규칙 3(유사 도서 회피)의 동작을 검증하려는 과정에서 중요한 문제가 발견되었다. 규칙 3이 발동하려면 "직전에 추천받은 도서"가 존재해야 하는데, 어떤 방법으로도 이 상황을 만들 수 없었던 것이다.

원인은 멱등 확인 로직에 있었다. 이 시점의 구현은 추천 이력에 행이 하나라도 있으면 무조건 그 책을 반환하도록 되어 있었다. 즉 학생이 첫 책을 받은 이후에는 영원히 그 책만 반환되며, 새로운 추천을 트리거할 방법이 존재하지 않았다. 결과적으로 규칙 3~5를 포함한 후보 선정 로직은 학생당 평생 딱 한 번, 그것도 직전 추천이 없는 상태(따라서 규칙 3이 무의미한 상태)에서만 실행되고 있었다.

**3. 원인 분석과 해소 경로**

이는 코드 자체의 오류가 아니라 미완성 상태의 필연적 귀결이었다. 학생이 책을 "다 읽었다"는 개념 자체가 아직 시스템에 없었기 때문이다. 완독을 표현할 수단이 없으니 추천 이력은 모두 동등하게 "받은 책"일 뿐이고, 따라서 다음 책을 줄 근거가 생기지 않는다.

이 문제는 2단계(문제풀이·채점) 구현으로 자연스럽게 해소된다. 추천 이력에 상태 값이 도입되어 완료와 진행 중을 구분할 수 있게 되면, 멱등 확인이 "진행 중인 책"만 대상으로 하게 되고 완료된 책은 더 이상 반환되지 않는다. 따라서 이 단계에서는 규칙 3~5의 SQL 조건이 논리적으로 정확한지만 파라미터를 직접 대입해 수동 검증하고, 실제 동작 검증은 2단계 완료 후로 미루었다.

### 19장 — 추천 로직 검증 (2/2) — 예외 상황 처리

**1. 잘못된 입력에 대한 응답**

존재하지 않는 학생 식별자로 추천을 요청하면 "학생의 소속 센터를 찾을 수 없습니다"라는 404 응답이 반환되는 것을 확인했다. 학생 식별자가 빈 문자열인 경우에는 400 검증 오류로 처리된다.

이 두 경우를 다른 상태 코드로 구분한 것은 클라이언트의 대응이 달라야 하기 때문이다. 빈 값은 화면의 입력 처리 오류이므로 재시도가 의미 있지만, 존재하지 않는 식별자는 학생 계정 자체의 문제이므로 센터 직원의 개입이 필요하다.

**2. 추천 불가 상황의 처리**

학생이 소속된 센터에 대여 가능한 도서가 하나도 없는 경우, "추천할 수 있는 도서가 더 이상 없습니다"라는 404 응답이 반환된다. 이 메시지는 학생 화면에 그대로 노출되므로, 학생이 상황을 이해하고 직원에게 문의할 수 있도록 기술 용어 없이 작성했다.

**3. 미구현 학년에 대한 동작 확인**

권장도서 순위가 등록되지 않은 학년(06, 07)에 속한 학생으로 추천을 요청하는 경우를 별도로 확인했다. 이 상황에서는 규칙 5의 학년 상향 루프가 상한까지 모두 공회전한 뒤 추천 불가로 종료되는데, 검증 결과 스택트레이스 노출 없이 정상적인 404 응답으로 마무리되는 것을 확인했다.

## VIII. 문제풀이 및 채점 (2026-07-09 ~ 07-10)

### 20장 — 채점 기준 및 결과 화면 설계 (1/2)

| | |
|---|---|
| **제 목** | 채점 기준 및 결과 화면 설계 (1/2) |

**1. 합격선의 비율 일반화**

문제은행 설계상 도서에 따라 문항 수가 12개 또는 15개로 다르다(7장). 초기에는 12문항 기준으로 합격선을 8개로 고정하려 했으나, 이 경우 15문항 도서에서는 상대적으로 쉬운 기준이 되어 도서 간 형평성이 깨진다.

이에 합격선을 절대 개수가 아니라 비율로 정의했다. 합격선은 전체 문항 수의 3분의 2를 올림한 값이며, 12문항에서는 8개, 15문항에서는 10개가 된다. 향후 다른 문항 수의 도서가 추가되더라도 코드 수정 없이 동일한 기준이 적용된다.

**2. 3등급 체계의 설계 의도**

채점 결과는 세 등급으로 나눈다. 전 문항을 맞히면 최상위 등급, 합격선 이상이면 합격 등급, 합격선 미만이면 재도전이다.

만점을 별도 등급으로 분리한 것은 학습 동기 설계 때문이다. 합격 여부만 판정하면 합격선을 넘긴 학생은 더 정확히 읽을 유인이 없다. 만점에 별도 명칭과 보상을 부여함으로써 이미 합격한 학생에게도 목표를 남겨두었다. 이 3등급 구분은 이후 뱃지 체계 재편(37장)에서도 그대로 승계되어, 등급별로 다른 뱃지가 부여되는 구조의 기반이 되었다.

**3. 등급별 결과 화면 구성**

결과 화면의 버튼 구성을 등급에 따라 다르게 했다. 최상위 등급은 심화문제와 메인 이동 두 개, 합격 등급은 심화문제·다시 풀기·메인 이동 세 개, 재도전은 다시 풀기와 메인 이동 두 개다.

합격 등급에만 "다시 풀기"를 남긴 것은 만점을 목표로 재도전할 여지를 주기 위해서다. 반대로 최상위 등급에는 다시 풀 이유가 없으므로 버튼을 제거해 화면을 단순화했다. 재도전 등급에는 심화문제 버튼을 노출하지 않는데, 기본 문항도 통과하지 못한 상태에서 심화 문항으로 넘어가는 것은 학습 순서상 맞지 않기 때문이다.

## IX. 채점 방식의 보안 강화 (2026-07-09)

### 22장 — 클라이언트 신뢰 방식의 취약점 진단

| | |
|---|---|
| **제 목** | 클라이언트 신뢰 방식의 취약점 진단 |
| **내 용** | 1. 기존 채점 구조의 문제<br>2. 취약점의 실제 확인<br>3. 전환 방향 결정 |

**1. 기존 채점 구조의 문제**

초기 구현에서 채점은 브라우저에서 이루어졌다. 화면이 문제와 정답을 모두 받아 학생의 선택과 비교한 뒤, 맞힌 개수와 전체 문항 수를 서버로 전송하면 서버는 그 값을 그대로 신뢰해 등급을 판정하고 보상을 지급했다.

이 구조는 서버 부담이 적고 구현이 간단하다는 장점이 있으나, 클라이언트가 보내는 값을 검증 없이 신뢰한다는 근본적 취약점을 갖는다. 브라우저 개발자 도구를 열 수 있는 사용자라면 실제로 몇 개를 맞혔는지와 무관하게 만점을 보고할 수 있다.

**2. 취약점의 실제 확인**

실제로 개발자 도구를 통해 전송 값을 조작해 보았고, 모든 문항을 틀린 상태에서도 만점 값을 보내면 서버가 이를 그대로 받아들여 최상위 등급을 부여하고 보상을 지급하는 것을 확인했다.

본 시스템에서 이 취약점의 영향은 단순한 점수 위조에 그치지 않는다. 만점 판정은 완독 처리를 유발하고, 완독은 다음 책 추천과 실물 도서 대여로 이어지며, 나아가 레벨 상승과 보상 카드 지급의 근거가 된다(39·41장). 즉 채점 결과 조작이 오프라인 실물 보상까지 연결되는 구조이므로 반드시 서버에서 검증해야 하는 사안이었다.

**3. 전환 방향 결정**

클라이언트는 학생이 각 문항에서 무엇을 선택했는지(문항 번호와 선택지)만 전송하고, 서버가 문제은행에서 실제 정답을 조회해 직접 대조하는 구조로 전환하기로 했다. 이 방식에서는 클라이언트가 점수를 계산할 필요도, 계산 결과를 신뢰받을 이유도 없어진다.

원인 파악을 위해 API를 직접 호출해 검증했으나 서버는 정상적으로 채점하고 있었다. 브라우저 자동화 도구로 새 세션을 만들어 화면 흐름 전체를 실행해도 정상 동작했다. 서버와 코드 어디에도 문제가 없는데 실사용자 환경에서만 장애가 발생하는 상황이었다.

이 재현 실패 자체가 중요한 단서였다. 검증에 사용한 환경은 모두 "처음 접속하는 새 브라우저"였고, 장애가 발생한 환경은 "이전에 여러 번 접속했던 브라우저"였다. 즉 문제는 코드가 아니라 클라이언트에 축적된 상태에 있었다.

**3. 근본 원인 규명**

원인은 PWA 서비스워커의 캐싱 전략이었다. 서비스워커가 정적 자원 요청을 캐시 우선 방식으로 처리하고 있었는데, 이 전략은 캐시에 저장된 파일이 있으면 네트워크를 확인하지 않고 그대로 반환한다. 그 결과 서버 채점 전환 이전 버전의 화면 스크립트가 계속 사용자에게 제공되고 있었다.

구 버전 스크립트는 맞힌 개수를 직접 전송하는 방식이므로, 23장에서 하위 호환을 차단한 서버가 이 요청을 400 오류로 거부한다. 그리고 스크립트의 오류 처리 코드는 요청이 실패하면 불합격으로 고정된 결과를 화면에 표시하도록 되어 있었다. 세 가지 요소가 연쇄해 "무엇을 맞혀도 재도전"이라는 현상이 만들어진 것이다.

## XI. 레벨 체계 1차 설계 (2026-07-10)

### 26장 — 레벨 구간 확장 설계

| | |
|---|---|
| **제 목** | 레벨 구간 확장 설계 |
| **내 용** | 1. 10단계 체계의 한계<br>2. 30단계로의 확장<br>3. 화면 연동과 진행률 계산 |

**1. 10단계 체계의 한계**

초기 레벨 체계는 1~10단계로, 입문·성장·마스터 세 구간으로 나뉘어 있었다. 그러나 이 체계에서는 한 단계를 올리는 데 필요한 학습량이 커서 학생이 진전을 체감하기 어려웠다. 초등 저학년 대상 서비스에서 몇 주에 한 번 레벨이 오르는 구조는 동기 유지에 불리하다고 판단했다.

**2. 30단계로의 확장**

이에 레벨을 30단계로 확장하고 구간을 1~10 입문, 11~20 성장, 21~30 마스터로 재편했다. 각 구간의 설명 문구는 기존 세 개를 그대로 승계했다. 문구가 구간의 성격을 이미 잘 표현하고 있어 변경할 이유가 없었고, 기존 사용자에게 일관된 경험을 주는 것이 낫다고 보았다.

단계별 필요 경험치는 80에서 시작해 최종 단계에서 5,760에 이르는 곡선으로 설정했다. 초반 구간의 간격을 좁게 두어 신규 학생이 빠르게 첫 레벨업을 경험하도록 하고, 후반으로 갈수록 간격을 넓혀 장기 목표로 기능하도록 설계했다.

**3. 화면 연동과 진행률 계산**

학생 메인 화면의 레벨 카드는 그동안 레벨 1, 경험치 0으로 고정된 임시 값을 표시하고 있었다. 이를 실제 계산 값으로 교체하면서 두 가지 지표를 제공하도록 했다. 하나는 현재 레벨 구간 내에서의 진행률이고, 다른 하나는 다음 레벨까지 남은 경험치를 학년별 권당 경험치로 나눈 "예상 권수"다.

진행률만 보여주면 학생이 무엇을 얼마나 해야 하는지 알 수 없으므로, "앞으로 몇 권을 더 읽으면 레벨이 오르는가"라는 행동 단위의 지표를 함께 제공한 것이다. 최고 레벨에 도달한 경우는 진행률 100퍼센트, 남은 권수 0으로 고정 처리했다.

레벨 데이터를 30단계로 확장하면서 관련 코드를 함께 점검하던 중, 레벨 계산 로직에 최고 레벨 값이 10으로 직접 기입되어 있는 것을 발견했다. 데이터는 30단계로 늘렸으나 코드는 여전히 10단계를 최대치로 간주하고 있었던 것이다.

원인은 설정값이 두 곳에 중복 정의되어 있었다는 데 있다. 레벨의 최대치는 데이터(레벨 정의 테이블의 행 수)에도 존재하고 코드(상수)에도 존재했으며, 두 값이 동기화된다는 보장이 없었다. 이는 특정 코드의 오류라기보다 설계상 단일 진실 공급원이 확보되지 않은 문제다.

**3. 재발 방지 기준 수립**

즉시 상수를 30으로 수정하는 한편, 레벨 관련 코드나 데이터를 변경할 때마다 유사하게 직접 기입된 값이 없는지 확인하는 것을 점검 항목으로 정했다.

이 문제의식은 이후 보상 체계 전면 재편(39·40장)에서 더 근본적으로 반영되었다. 재편된 체계에서는 레벨을 저장하지 않고 완독 권수로부터 매번 계산하도록 하여 값이 어긋날 여지 자체를 없앴고, 레벨 규칙 역시 테이블이 아니라 코드 상수로 일원화했다.

**2. 숨김 처리가 동작하지 않는 문제**

화면 작업 중 요소 숨김이 적용되지 않는 문제가 반복적으로 발생했다. 원인은 CSS 우선순위였다. 표준 숨김 속성은 요소를 표시하지 않도록 지정하지만, 해당 요소의 클래스에 표시 방식이 직접 지정되어 있으면 클래스 규칙이 우선해 숨김이 무시된다.

이 문제는 결과 화면의 등급별 버튼 제어(20장)처럼 요소를 조건부로 노출하는 모든 지점에서 발생할 수 있어, 화면별 스타일시트 최상단에 숨김 속성이 항상 우선하도록 하는 규칙을 명시적으로 선언하는 것을 표준 절차로 정했다.

**3. 화면 구성 요소 누락 사례**

추천 도서 카드 영역을 서버 렌더링에서 동적 로딩 방식으로 변경하는 과정에서, 분류·수상정보·교과 수록·추천기관·태그로 구성된 메타 정보 영역이 통째로 누락된 채 배포된 사례가 있었다. 서버 렌더링에서는 템플릿에 있던 항목들이 동적 렌더링 함수로 옮겨지면서 빠진 것이다.

### 30장 — 실시간 모니터링 요구사항 정의

| | |
|---|---|
| **제 목** | 실시간 모니터링 요구사항 정의 |
| **내 용** | 1. 기능의 도입 배경<br>2. 화면 구성 설계<br>3. 초기 구현 방식과 그 한계 |

**1. 기능의 도입 배경**

실시간 모니터링은 센터 직원이 현재 클리닉 수업에 참여 중인 학생들의 상태를 한 화면에서 파악하기 위한 기능이다. 오프라인 센터에서는 직원이 교실을 돌며 학생들의 진행 상황을 확인하는데, 학생이 지금 어떤 책을 읽고 있는지, 문제를 풀었는지, 도움이 필요한 상태인지를 시스템이 보여주면 개입이 필요한 학생에게 집중할 수 있다.

이 기능은 관리자 화면 11개 중 학생의 학습 데이터와 가장 밀접하게 연결된 화면이며, 실시간성이 요구된다는 점에서 다른 관리 화면과 성격이 다르다.

**2. 화면 구성 설계**

화면은 학생별 카드를 격자로 배치하는 형태로 설계했다. 각 카드에는 학생 이름, 현재 진행 중인 도서, 경과 시간, 획득 뱃지 수가 표시된다. 상단에는 센터·일자·교시 필터를 두었다.

교시 개념을 필터로 둔 것은 센터의 운영 방식 때문이다. 클리닉 수업은 1교시부터 4교시까지 고정된 시간대로 운영되며, 직원은 현재 교시에 해당하는 학생들만 보면 된다. 3장에서 시간 슬롯을 상수화해 둔 것이 여기서 사용된다.

**3. 초기 구현 방식과 그 한계**

초기 구현은 학생이 로그인하는 시점에 모니터링 카드를 생성하는 방식이었다. 구현이 단순하고 별도의 사전 데이터가 필요 없다는 장점이 있었다.

그러나 이 방식은 운영 실태와 맞지 않았다. 센터의 클리닉 수업은 사전 예약제로 운영되므로 직원은 수업 시작 전에 "오늘 이 교시에 몇 명이 오기로 되어 있는가"를 알아야 하고, 그중 누가 아직 오지 않았는지를 파악해야 한다. 로그인 시점에 카드를 만드는 방식에서는 이미 도착한 학생만 화면에 나타나므로, 미도착 학생의 존재 자체를 알 수 없다. 이 한계는 예약 기반 구조로의 재설계(31장)로 이어졌다.

## XIII. 예약 기반 모니터링 재설계 (2026-07-23)

### 31장 — 예약 개념 도입 및 상태 전이 재정의

**1. 예약 테이블 신설**

모니터링을 예약 기반으로 전환하기 위해 클리닉 예약 테이블을 신설했다. 구성은 학생 식별자, 예약 일자, 시간 슬롯(교시) 세 컬럼으로 단순하게 두었다. 예약이라는 개념이 본 시스템에서는 "이 학생이 이 날 이 교시에 오기로 되어 있다"는 사실만 표현하면 충분하고, 예약 변경 이력이나 취소 사유 같은 정보는 현재 운영 방식에서 요구되지 않았기 때문이다.

이 테이블이 생기면서 모니터링 화면은 로그인 여부와 무관하게 "오늘 이 교시에 올 예정인 학생 전원"의 카드를 미리 표시할 수 있게 되었다. 아직 오지 않은 학생은 미입실 상태로 표시되므로, 직원이 결석자를 즉시 파악할 수 있다.

**2. 입실 판정 시점의 재정의**

미입실에서 입실로 전환되는 시점을 로그인이 아니라 도서 추천 API 호출 시점으로 정했다. 이는 언뜻 이상해 보이지만 실제 운영 흐름을 반영한 결정이다.

학생이 로그인만 하고 실제 활동을 시작하지 않는 경우가 있다. 화면을 잘못 눌렀거나, 로그인해 놓고 다른 일을 하는 경우다. 반면 도서 추천이 호출되었다는 것은 학생이 메인 화면에 진입해 오늘의 학습을 시작했다는 뜻이므로, 직원이 알고 싶어 하는 "실제로 활동을 시작했는가"에 더 정확히 대응한다.

📷 코드 캡쳐: `ClinicService.recommendBook()` — 모니터링 입실 상태 갱신 연동부

**3. 범위 한정 결정과 그 영향**

이번 작업에서는 데이터 구조와 모니터링 로직만 구현하고, 관리자가 예약을 실제로 등록하는 화면은 범위에서 제외하기로 명시적으로 결정했다. 개발 일정상 모니터링 로직 검증을 우선하기 위한 판단이었다.

다만 이 결정은 명확한 부작용을 동반한다. 예약 등록 화면이 없으면 예약 테이블이 비어 있고, 따라서 실제 운영 데이터로는 모니터링 화면에 카드가 하나도 표시되지 않는다. 검증은 예약 테이블에 직접 데이터를 삽입해 수행해야 하며, 이후 "모니터링 화면에 학생이 보이지 않는다"는 문의가 발생하면 장애가 아니라 예약 등록 기능의 부재가 원인임을 먼저 확인해야 한다. 이 사항을 인수인계 항목으로 기록해 두었다.

## XIV. 실시간 동기화 장애 대응 (2026-07-24)

### 33장 — 무증상 동기화 실패의 발견

| | |
|---|---|
| **제 목** | 무증상 동기화 실패의 발견 |
| **내 용** | 1. 이상 징후의 포착<br>2. 예외를 삼키는 구조의 문제<br>3. 실패 원인 규명 |

**1. 이상 징후의 포착**

실시간 모니터링 화면은 실시간 동기화를 주 경로로, 30초 주기 폴링을 보조 경로로 사용하도록 설계되었다. 그런데 화면이 정상 동작하는 것처럼 보이면서도 갱신이 항상 30초 단위로만 이루어지는 현상이 관찰되었다. 실시간 경로가 동작하지 않고 보조 경로만으로 화면이 유지되고 있었던 것이다.

**2. 예외를 삼키는 구조의 문제**

원인 추적이 늦어진 이유는 동기화 처리가 예외를 내부에서 처리하고 넘어가는 구조였기 때문이다. 이 구조 자체는 의도된 것이었다. 실시간 동기화가 실패하더라도 데이터베이스 트랜잭션은 정상적으로 완료되어야 하므로, 동기화 실패가 본 처리를 중단시키지 않도록 예외를 격리한 것이다.

그러나 예외를 격리하면서 기록도 남기지 않은 것이 문제였다. 그 결과 동기화가 매번 실패하고 있음에도 로그에 아무 흔적이 남지 않았고, 화면은 보조 경로 덕분에 정상으로 보였다. 이 사례는 "실패해도 계속 진행하는" 설계가 "실패를 인지할 수 없는" 설계가 되지 않도록 반드시 기록을 남겨야 한다는 점을 보여준다.

**3. 실패 원인 규명**

원인은 데이터 직렬화 과정에 있었다. 실시간 동기화는 서버의 데이터 객체를 외부 저장소 형식으로 변환해 전송하는데, 이 변환이 객체 내부를 자동으로 탐색하는 방식으로 이루어진다. 그런데 전송 대상 객체에 자바의 날짜·시간 타입이 포함되어 있었고, 해당 타입은 런타임 환경의 모듈 접근 제한으로 인해 자동 탐색이 차단되어 변환 시점에 예외가 발생했다.

구체적으로는 학생 카드 정보에 포함된 도서 목록의 추천 시각 필드가 원인이었다. 이 필드가 추가된 시점 이후 모든 실시간 동기화가 실패하고 있었으며, 약 하루 동안 인지되지 않은 상태로 지속되었다.

### 34장 — 외부 SDK 로딩 문제 해결

| | |
|---|---|
| **제 목** | 외부 SDK 로딩 문제 해결 |
| **내 용** | 1. 브라우저 측 SDK 로딩 실패<br>2. 로컬 번들 구성<br>3. 내부 참조 경로 치환 |

**1. 브라우저 측 SDK 로딩 실패**

서버 측 직렬화 문제와 별개로, 브라우저 쪽에서도 실시간 동기화가 성립하지 않는 문제가 있었다. 모니터링 화면이 실시간 저장소에 접속하려면 클라이언트 SDK를 로드해야 하는데, 이 SDK를 외부 CDN에서 가져오는 방식이 해당 네트워크 환경에서 차단되었다.

즉 실시간 동기화는 서버 측(직렬화 실패)과 클라이언트 측(SDK 로드 실패) 양쪽에서 동시에 막혀 있었고, 이것이 원인 파악을 복잡하게 만든 요인이었다. 한쪽만 고쳐서는 증상이 개선되지 않기 때문이다.

**2. 로컬 번들 구성**

CDN 의존을 제거하기 위해 SDK를 프로젝트 정적 자원 디렉터리에 직접 포함시켰다. 외부 네트워크 상황과 무관하게 동작하도록 하기 위한 조치이며, 센터의 네트워크 환경이 기관마다 다를 수 있다는 점을 고려하면 운영 안정성 측면에서도 타당한 선택이었다.

**3. 내부 참조 경로 치환**

한 레벨을 올리는 데 필요한 권수를 학년별로 다르게 설정했다. 초1과 초2는 8권, 초3은 5권, 초4부터 초6까지는 4권이다.

저학년일수록 많은 권수를 요구하는 것은 도서의 분량 차이 때문이다. 저학년 대상 도서는 분량이 짧아 단시간에 읽을 수 있으므로, 같은 권수를 기준으로 하면 저학년의 레벨이 지나치게 빠르게 상승한다. 실제 학습 투입 시간이 학년과 무관하게 비슷하도록 권수를 조정한 것이다.

추천 알고리즘이 학생의 학년에 맞는 도서를 배정하므로(16장) 학년이 섞이는 문제는 발생하지 않는다. 진도가 빠른 학생은 학생의 학년 설정 자체를 상향하는 운영 절차로 대응한다.

## XVI. 독서 카드 수집 기능 (2026-07-27 ~ 07-28)

### 41장 — 카드 수집 기능 설계

| | |
|---|---|
| **제 목** | 독서 카드 수집 기능 설계 |
| **내 용** | 1. 온·오프라인 연계 보상 구조<br>2. 카드 2종 설계<br>3. 수집 과정의 연출 |

**1. 온·오프라인 연계 보상 구조**

독서 카드는 온라인 성취를 오프라인 실물 보상으로 연결하는 장치다. 학생이 책을 완독하면 온라인에서 카드를 한 장 얻고, 카드를 10장 모으면 센터에서 실물 카드 1장을 받는 구조다.

이 구조에서 중요한 설계 판단은 시스템의 책임 범위를 어디까지로 할 것인가였다. 결론은 시스템이 진행도 표시와 달성 알림까지만 담당하고, 실물 지급과 그에 따른 카드 소모 처리는 오프라인 수동 절차로 남기는 것이었다. 실물 지급 여부를 시스템이 관리하려면 직원이 지급 시마다 시스템에 기록해야 하는데, 이 절차가 누락되면 데이터가 실제와 어긋나 오히려 혼란을 키운다고 판단했다.

**2. 카드 2종 설계**

카드는 두 종류로 구성했다. 일반 카드는 완독한 책마다 한 장씩 부여되며 책당 종류가 고정된다. 즉 어떤 책을 읽으면 그 책에 대응하는 카드를 얻는 방식이라 카드 수집이 곧 독서 기록이 된다.

희귀 카드는 일반 카드를 10장 모을 때마다 추가로 부여되며 특정 도서와 무관하다. 실물 교환 기준과 동일한 10장 주기로 설정해, 실물을 받는 시점에 온라인에서도 특별한 보상을 함께 얻도록 했다.

**3. 수집 과정의 연출**

결과 화면에서 카드를 획득할 때는 카드의 정체를 즉시 공개하지 않고 가린 상태로 현재 진행도만 표시한다. 반면 메인 화면의 수집함에서는 획득한 카드 이미지만 나열하고 제목이나 진행도 텍스트를 두지 않았다.

이렇게 나눈 것은 두 화면의 역할이 다르기 때문이다. 결과 화면은 성취 직후의 순간이므로 기대감을 유지하는 연출이 적합하고, 수집함은 그동안 모은 것을 감상하는 공간이므로 텍스트 없이 이미지만 배열하는 편이 수집의 만족감을 준다.

카드 기능의 초기 구현은 별도 테이블 없이 추천 이력에서 완독 건을 세어 카드 보유 현황을 계산하는 방식이었다. 39장에서 레벨을 저장하지 않고 계산하도록 한 것과 같은 접근이다.

**2. 지급 이력 테이블 도입**

이에 카드 지급 이력을 기록하는 별도 테이블을 도입했다. 대리 키를 기본 키로 두고, 일반 카드인 경우에만 도서 식별자를 기록하며, 카드 종류와 희귀 카드 발급을 유발한 누적 수치를 함께 저장한다.

카드 보유 현황 조회는 기존의 파생 계산 방식을 폐기하고 이 테이블을 기준으로 재계산하도록 변경했다.

**3. 데이터베이스 수준의 중복 차단**

중복 지급 방지를 애플리케이션 코드가 아니라 데이터베이스 제약으로 구현했다. 일반 카드는 학생과 도서 조합이 유일해야 하고, 희귀 카드는 학생과 발급 유발 수치의 조합이 유일해야 한다. 두 규칙을 조건부 유일 인덱스 두 개로 표현했다.

코드 검사만으로 중복을 막지 않은 것은 21장에서 다룬 재제출 상황이나 동시 요청 상황에서 검사와 삽입 사이에 경합이 발생할 수 있기 때문이다. 데이터베이스 제약은 이러한 경합 상황에서도 유일성을 보장한다. 카드가 실물 보상으로 이어지는 만큼 중복 지급의 비용이 크다는 점도 고려했다.

## XVII. 데이터 규약 정비 (2026-07-28)

### 43장 — 시간대 처리 규약 확립

| | |
|---|---|
| **제 목** | 시간대 처리 규약 확립 |

**1. 날짜 불일치 현상의 발견**

오전 시간대에 개발 환경을 기동했을 때, 오늘 날짜로 생성되어야 할 예약 데이터가 전날 날짜로 저장되는 현상이 발견되었다. 그 결과 모니터링 화면에서 오늘의 예약을 조회해도 아무것도 표시되지 않았다.

**2. 원인 분석 — 서버 시간대와 응용 시간대의 차이**

원인은 데이터베이스 서버와 애플리케이션이 서로 다른 시간대를 기준으로 동작하고 있었다는 점이다. 데이터베이스가 실행되는 환경은 협정 세계시를 사용하고, 애플리케이션의 날짜 계산은 한국 표준시를 기준으로 하고 있었다.

두 시간대는 9시간 차이가 나므로, 한국 시간 기준 오전 9시 이전에는 데이터베이스가 인식하는 날짜가 애플리케이션이 인식하는 날짜보다 하루 이르다. 데이터 적재 시 데이터베이스의 현재 날짜 함수를 사용했기 때문에 전날 날짜로 저장되었고, 조회는 애플리케이션이 계산한 오늘 날짜로 이루어져 일치하는 데이터가 없었던 것이다.

같은 문제가 월간 집계 쿼리에도 존재함을 확인했다. 매월 1일 오전에 집계를 수행하면 전월의 마지막 날로 인식되어 집계 범위가 어긋난다.

**3. 통일 규약 수립**

이에 본 시스템의 모든 시간과 날짜를 한국 표준시 기준으로 통일하는 규약을 수립했다. 데이터베이스 쿼리에서 서버 로컬 시간을 반환하는 함수의 사용을 금지하고, 협정 세계시에 9시간을 더하는 형태를 표준으로 사용하도록 했다. 이 방식은 데이터베이스 서버가 어느 시간대로 설정되어 있든 항상 동일한 결과를 보장한다.

기존 쿼리 전체를 점검해 해당 함수 사용처를 모두 교체하고, 이후 새 쿼리 작성 시에도 처음부터 표준 형태를 사용하도록 규약을 문서화했다.

독서일지는 학생이 센터에서 보낸 각 수업 회차의 기록을 남기는 기능이다. 어느 교시에 참여했는지, 어떤 활동을 했는지, 지도 교사의 메모는 무엇인지를 날짜 단위로 축적한다.

이 기록의 주된 용도는 학부모 상담이다. 학생의 학습 이력을 설명할 때 완독 권수나 레벨 같은 집계 지표만으로는 개별 수업에서 무슨 일이 있었는지 알 수 없으므로, 회차별 기록이 필요하다.

**2. 화면 구성**

독서일지 화면은 날짜별 목록과 상세 기록으로 구성했다. 목록에서 학생 이름 옆에 도움이 필요한 상태를 나타내는 표식을 두어, 직원이 목록만 훑어도 주의가 필요한 학생을 파악할 수 있도록 했다.

**3. 모니터링 화면과의 역할 분담**

독서일지 화면과 실시간 모니터링 화면은 같은 데이터를 다루지만 역할을 명확히 나누었다. 모니터링은 현재 진행 중인 수업을 대상으로 하며 상태를 변경할 수 있는 화면이고, 독서일지는 누적된 기록을 조회하는 화면으로 상태 변경 기능을 두지 않았다.

역할을 분리한 것은 같은 값을 두 화면에서 수정할 수 있으면 어느 쪽이 최신인지 판단하기 어려워지기 때문이다. 특히 도움 필요 상태는 현재 상태와 과거 기록이라는 두 성격을 동시에 갖는 값이라 이 구분이 중요했으며, 이는 다음 장에서 별도로 다룬다.

### 46장 — 상태값과 스냅샷의 이중 저장 구조

| | |
|---|---|
| **제 목** | 상태값과 스냅샷의 이중 저장 구조 |
| **내 용** | 1. 단일 저장 구조의 문제<br>2. 이중 저장 구조의 도입<br>3. 저장·조회 경로의 정리 |

**1. 단일 저장 구조의 문제**

"혼자 읽기 어려워요"로 표현되는 도움 필요 상태는 처음에 독서일지 테이블에만 저장되었다. 즉 그날의 기록으로만 존재했다.

그런데 실제 운영에서 이 값은 하루짜리 기록이 아니었다. 어떤 학생이 혼자 읽기 어려운 상태라면 그것은 다음 수업에도, 그다음 수업에도 이어지는 지속적 특성이다. 일지에만 저장하는 구조에서는 새 수업이 시작될 때마다 값이 초기화되어, 직원이 매 수업마다 같은 학생을 다시 체크해야 했다. 지속적으로 도움이 필요한 학생일수록 반복 입력 부담이 커지는 구조였다.

**2. 이중 저장 구조의 도입**

이에 같은 값을 두 곳에 저장하는 구조로 변경했다. 학생 테이블에는 현재 상태를 나타내는 컬럼을 두고, 독서일지 테이블에는 그날 시점의 스냅샷을 유지한다.

두 값의 성격은 다르다. 학생 테이블의 값은 현재 상태이므로 해제하기 전까지 계속 유지되며, 다음 수업에도 켜진 채로 표시된다. 독서일지의 값은 그날의 기록이므로 이후 상태가 해제되어도 과거 일지에는 그대로 남는다. 이렇게 하면 "지금 도움이 필요한 학생은 누구인가"와 "그날 이 학생은 어떤 상태였는가"라는 서로 다른 두 질문에 모두 정확히 답할 수 있다.

**3. 저장·조회 경로의 정리**

이중 저장은 두 값이 어긋날 위험을 동반하므로 갱신과 조회 경로를 명확히 규정했다.

저장 시에는 상태 값 갱신과 일지 스냅샷 기록이 한 처리 안에서 함께 이루어진다. 일지 헤더가 새로 생성되는 경우에는 학생 테이블의 현재 상태를 스냅샷으로 복사한다. 상태를 변경하는 조작은 실시간 모니터링 화면에서만 가능하며, 독서일지 화면의 일괄 저장 처리는 이 컬럼을 건드리지 않도록 명시적으로 제외했다.

조회 시에는 모니터링 카드가 학생 테이블의 현재 상태를 읽고, 독서일지 목록은 일지의 스냅샷을 우선하되 값이 없으면 현재 상태로 대체하는 방식을 쓴다. 과거 날짜에 대해서는 당시 스냅샷이, 스냅샷이 없는 경우에는 현재 상태가 표시된다.

### 48장 — 결제 시스템 도입 배경 및 이용권 모델

| | |
|---|---|
| **제 목** | 결제 시스템 도입 배경 및 이용권 모델 |
| **내 용** | 1. 도입 배경<br>2. 이용권 개념의 설계<br>3. 도메인 분리와 테이블 구성 |

**1. 도입 배경**

본 과제는 초기 계획에서 학습 기능 중심으로 범위가 잡혀 있었고, 결제 기능은 포함되어 있지 않았다. 그러나 서비스 오픈을 앞두고 수강료 수납을 시스템에서 처리해야 한다는 요구가 확정되면서 결제와 이용권 관리가 새로운 범위로 추가되었다.

이 변경은 초기 기능 정의 문서에 반영되어 있지 않으므로, 이후 일정과 우선순위를 판단할 때는 해당 문서만 참조해서는 안 되며 실제 개발 이력을 함께 확인해야 한다는 점을 기록해 둔다.

**2. 이용권 개념의 설계**

결제 결과를 직접 학습 권한과 연결하지 않고, 그 사이에 이용권이라는 개념을 두었다. 결제가 이루어지면 이용권이 발급되고, 학습 기능의 사용 가능 여부는 이용권의 상태로 판단한다.

이 중간 계층을 둔 이유는 결제와 이용 권한이 항상 일대일로 대응하지 않기 때문이다. 한 번의 결제가 여러 회차의 이용권을 만들 수도 있고, 결제 없이 관리자가 이용권을 부여하는 경우(체험 수업 등)도 있으며, 환불 시에는 결제를 취소하면서 이용권만 회수해야 하는 상황도 생긴다. 두 개념을 직접 연결하면 이러한 경우마다 예외 처리가 필요하지만, 이용권을 독립적으로 두면 결제 쪽 변화와 무관하게 권한 판단 로직을 유지할 수 있다.

**3. 도메인 분리와 테이블 구성**

이에 따라 결제와 이용권을 각각 별도 도메인 패키지로 분리했다. 결제 도메인은 결제 요청·승인·취소와 외부 결제 서비스 연동을 담당하고, 이용권 도메인은 발급·사용·만료 상태 전이를 담당한다. 테이블도 결제 이력과 이용권을 분리해 구성했다.

### 50장 — 환불 처리 및 이용권 회수

| | |

| **제 목** | 환불 처리 및 이용권 회수 |

**1. 환불 요청 흐름**

환불은 관리자 화면에서 시작된다. 담당자가 대상 결제 건을 선택해 환불을 요청하면 시스템이 외부 결제 서비스에 환불을 요청하고, 결과를 받아 결제 상태를 갱신한다.

환불 권한을 학생이나 학부모가 아닌 관리자에게만 부여한 것은, 오프라인 수업 서비스의 특성상 환불 가능 여부와 금액이 수업 진행 상황에 따라 달라지기 때문이다. 이 판단은 시스템이 자동으로 할 수 없으므로 담당자의 확인을 거치도록 했다.

**2. 이용권 회수 처리**

환불이 완료되면 해당 결제로 발급된 이용권을 회수 상태로 전환한다. 결제와 이용권을 분리해 둔 설계(48장)가 여기서 효과를 발휘하는데, 결제 취소와 이용권 회수를 각각의 도메인에서 처리하면서도 하나의 트랜잭션으로 묶을 수 있었다.

이미 사용된 이용권이 포함된 경우의 처리는 별도 검토가 필요한 사항으로, 환불 가능 범위를 어떻게 산정할지는 운영 정책과 함께 정해야 한다.

**3. 이력 보존 원칙**

환불 처리 시 기존 결제 기록을 수정하거나 삭제하지 않고 환불 이력을 별도로 남기는 방식을 택했다. 금전이 오간 기록은 추후 확인 요청이나 분쟁 발생 시 근거가 되어야 하므로, 어떤 경우에도 원본이 유실되지 않도록 했다. 8장에서 도서 데이터에 논리 삭제를 적용한 것과 같은 원칙이다.
