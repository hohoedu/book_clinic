## 1. 센터 간 권한 우회(IDOR) — 관리자 API 5종

**심각도**: 치명적 — 타 센터 학생의 예약·출결·학습기록을 임의로 조작 가능

### 재현

`branch2`(DAE001 관리자)로 로그인한 세션에서 PUS002 학생을 대상으로 호출:

```
POST /admin/monitor/reservation/register  {"studentId":"PUS002T14","slotInstanceId":5}
  → 200. PUS002 학생이 DAE001 슬롯에 예약 생성됨
POST /admin/monitor/reservation/cancel    {"studentId":"PUS002T13","reservationId":1,"reason":"x"}
  → 200. DB에서 실제로 CANCELED로 전환됨
POST /admin/monitor/exit                  {"studentId":"PUS002T13"}
  → 200. 타 센터 학생이 강제 퇴실 처리됨
```

`diary`, `quiz/reset`도 코드 패턴이 동일함을 확인(요청 본문 studentId를 센터 검증 없이 그대로 사용).
특히 `quiz/reset`은 **뒤에 추천받은 책까지 연쇄 삭제**하고 뱃지·카드를 회수하므로, 타 센터 학생의 학습 이력을 통째로 날릴 수 있었다.

### 원인

`ReservationAdminController`의 조회 API(list/summary/slots/students)는 `requireCenterCode(userDetails)`의 **반환값을 실제 쿼리 조건으로 사용**해 자연스럽게 센터 스코핑이 걸린다. 반면 처리 API는

```java
requireCenterCode(userDetails);          // ← 호출만 하고 반환값을 버림
reservationService.reserveByAdmin(reqDTO.getStudentId(), ...);  // 요청 본문을 그대로 신뢰
```

로그인 여부만 확인하고 **대상 학생이 내 센터 소속인지는 확인하지 않았다.** `MonitorController.exit`은 `@AuthenticationPrincipal`을 받지도 않아 센터 정보에 접근조차 하지 않았다.

즉 "대상을 세션에서 가져오는 API"와 "요청 본문에서 가져오는 API"의 차이를 인지하지 못한 것이 원인이며, 후자에만 검증이 필요했다.

### 수정

**신규**: `_core/auth/CenterAccessGuard.java`

```java
public String requireCenterCode(CustomUserDetails userDetails)              // 401
public String requireStudentInMyCenter(CustomUserDetails userDetails, String studentId)
    // 없는 학생 → 404, 타 센터 학생 → 403, 통과 시 centerCode 반환
```

컨트롤러마다 private 헬퍼를 복사해두면 한쪽만 고쳐지는 상황이 재발하므로 공용 빈으로 분리했다. `ReservationAdminController`의 기존 private `requireCenterCode`는 이 가드로 대체(조회 API 5개 동작 변화 없음).

| 엔드포인트 | 위치 | 조치 |
|---|---|---|
| `POST /admin/monitor/reservation/register` | ReservationAdminController.java:97 | `requireStudentInMyCenter` |
| `POST /admin/monitor/reservation/cancel` | ReservationAdminController.java:108 | `requireStudentInMyCenter` |
| `POST /admin/monitor/exit` | MonitorController.java:52 | `requireStudentInMyCenter` |
| `POST /admin/monitor/diary` | MonitorController.java:65 | `requireStudentInMyCenter` + 항목 2 |
| `POST /admin/monitor/quiz/reset` | MonitorController.java:77 | `requireStudentInMyCenter` |

부수 정리로 `diary`/`quiz/reset`의 `Authentication` 파라미터를 `@AuthenticationPrincipal CustomUserDetails`로 통일했다. `authentication.getName()`은 `CustomUserDetails.getUsername()` = `loginUser.getUserId()`와 같은 값이라 staffName 기록값은 변하지 않는다.

## 2. 독서일지 sessionId / studentId 미대조

**심각도**: 치명적 — 항목 1을 고쳐도 남는 우회 경로

### 재현

`saveDiary`는 `sessionId`와 `studentId`를 **둘 다 요청으로 받으면서 서로 맞는지 확인하지 않는다.** 따라서 컨트롤러에서 studentId의 센터만 막아도, *내 센터 학생 id + 남의 센터 sessionId* 조합이면 그 세션의 일지를 그대로 덮어쓸 수 있다.

```
POST /admin/monitor/diary  {"sessionId": <PUS002 학생의 세션>, "studentId":"DAE001T01", "memo":"..."}
```

### 원인

`MonitorService.saveDiary`가 `upsertDiary(req.getSessionId(), ...)`로 sessionId를 그대로 사용한다. sessionId는 연속된 정수라 추측이 쉽다.

### 수정

`saveDiary` 진입부에서 기존 매퍼(`findCardBySessionId`)를 재사용해 세션의 실제 주인과 대조한다(새 쿼리 추가 없음).

```java
MonitorRespDTO.CardDTO session = monitorRepository.findCardBySessionId(req.getSessionId());
if (session == null) throw new Exception404("독서일지를 저장할 세션을 찾을 수 없습니다: sessionId=" + ...);
if (!session.getStudentId().equals(req.getStudentId())) throw new Exception403("해당 학생의 세션이 아닙니다.");
```

### 검증

```
[T7 내센터 학생id + 남의 세션 diary]  403 해당 학생의 세션이 아닙니다
[R6 없는 sessionId diary]            404 독서일지를 저장할 세션을 찾을 수 없습니다
[T5 정상 경로(실제 세션)]             200, DB에 정상 1건만 기록
```

## 5. 동시 요청으로 "하루 1회차" 제약 우회

**심각도**: 심각 — 4회권 한 달치를 하루에 전부 소진시킬 수 있었음

### 재현 (수정 전)

같은 학생이 서로 다른 4개 슬롯을 동시에 POST → **4건 전부 성공**. 순차 요청이면 정상 차단된다.

### 원인

`ReservationService.reserveOne`에서 두 검사의 구현 방식이 달랐다.

```java
// 평문 SELECT — 이 시점과 INSERT 사이에 다른 요청이 끼어들 수 있다 (TOCTOU)
if (repository.countOtherReservedOnDate(studentId, serviceDate, slotInstanceId) > 0) { ... }

// 조건부 UPDATE (WHERE reserved_count < capacity) — DB 행 락이 직렬화해준다
int updated = repository.incrementReservedCount(slotInstanceId);
```

최종 방어선인 `UX_reservation_slot_student`는 `(slot_instance_id, student_id)` 기준이라 **같은 슬롯 중복만** 막는다. 서로 다른 슬롯이면 걸리지 않았다.

> **정원(capacity) 초과는 원래부터 발생하지 않는다** — 정원 10인 슬롯에 15건을 동시 요청해 정확히 10건만 통과하는 것을 확인했다. 조건부 UPDATE 설계가 의도대로 동작하고 있으며, 이 항목은 "하루 1회차" 규칙에만 해당했다.

### 수정

정원과 같은 원리(확인과 기록을 DB 제약 한 겹으로)를 학생별 규칙에도 적용했다.

- `erp_bookstore_reservation`에 `service_date DATE NOT NULL` 추가 — 유니크 인덱스는 조인한 컬럼에 걸 수 없어, 날짜가 예약 행 자체에 있어야 제약이 성립한다. 값은 항상 슬롯에서 복사한다(호출자가 넣지 못하게 `reserveOne`이 `slot.getServiceDate()`로 채운다).
- 필터링 유니크 인덱스 `UX_reservation_student_date (student_id, service_date) WHERE status IN ('RESERVED','ATTENDED','NOSHOW')` — 상태 집합은 `countOtherReservedOnDate`와 동일하게 맞췄다.
- 기존 `countOtherReservedOnDate` 선검사는 **사용자에게 이유를 설명하는 용도**로 남기고, 실제 강제는 인덱스가 한다. `DuplicateKeyException` catch 문구를 두 인덱스 모두를 포괄하도록 바꿨다.

### 검증

```
서로 다른 4개 슬롯 동시 요청 → (106, 200 OK) / 나머지 3건 400 "이 날짜엔 이미 예약이 있습니다"
확정된 예약 수 = 1   (수정 전: 4)
정원 회귀: 정원 10 슬롯에 15건 동시 → 정확히 10건 성공
```

## 6. 문제 정답이 비로그인으로 노출

**심각도**: 심각

### 재현 (수정 전)

`GET /question/search?contentId=5&qlevel=01` — 로그인 없이 200, 응답에 `"ans":"2"` 그대로 포함.

### 원인 및 제약

이 엔드포인트는 **학생 문제풀이 화면과 관리자 도서 데이터 화면이 함께 쓴다.** 학생 화면 때문에 permitAll이라 정답까지 새어나갔다. 그런데 단순히 `ans`를 빼면 화면이 깨진다 — `student-question.js`가 `q.ans`로 두 가지를 계산하고 있었다.

- 서버 채점 실패 시 폴백 표시용 정답 수
- **"틀린 문제 풀기"에 쓸 오답 문항 번호(`wrongQnums`)** ← 실제 기능

### 수정

정답을 화면에서 걷어내되 기능을 유지하기 위해 서버가 오답 목록을 내려주도록 먼저 바꿨다.

1. `ClinicService.submitQuiz`가 이미 문항별 정오답(`answerLogs`)을 계산하고 있으므로, 그걸로 `wrongQnums`를 만들어 `QuizSubmitRespDTO`에 담는다(새 쿼리 없음).
2. `student-question.js`가 `q.ans` 대신 서버 응답의 `wrongQnums`를 쓰도록 변경. 채점 호출이 실패한 폴백 경로는 정답을 모르므로 0점·재도전으로 표시하고 오답 목록은 비운다.
3. `/question/search`는 인증된 관리자에게만 `ans`를 채워 보내고, 그 외에는 `null`로 비운다. 문제 편집 화면(`book-data.js`)은 그대로 동작한다.

### 검증

```
학생 세션   ans: [None, None, None, None, None]
관리자      ans: ['2', '3', '3', '3', '3']
전부오답 제출 → correct=0/12  wrongQnums=['01'...'12']
전부정답 제출 → correct=12/12 grade=KING  wrongQnums=[]
```

## 7. 지난 회차 예약 가능 → 입실 불가 (데드엔드)

**심각도**: 중간

### 재현 (수정 전)

14:21에 13:00 회차가 `status: OPEN`으로 내려오고 예약도 200으로 성공했다. 그런데 입실은 회차 시간대에만 되므로(`markAttended`) **이용권만 묶인 채 아무것도 못 하는 상태**가 됐다. 하루 1회차 제약 때문에 그날 다른 회차를 새로 잡을 수도 없었다.

### 수정

- 슬롯 목록 쿼리(`findOpenSlots`, `findSlotsByDates`)에서 이미 끝난 회차의 status를 `CLOSED`로 계산해 내려준다. 기준 시각은 `ends_at` — 이미 시작한 회차는 아직 입실이 가능하므로 끝나기 전까지는 열어둔다. 관리자 화면은 `status !== "OPEN"`을 이미 "마감"으로 그리므로 화면 수정이 필요 없다.
- 목록만 고치면 API 직접 호출로 우회되므로 `reserveOne`에서도 `ends_at` 경과를 400으로 막는다. 직원 대리 예약도 같은 규칙을 탄다(지난 회차로 잡아주면 그 학생은 입실을 못 하기 때문).

### 검증

```
오늘 슬롯 status: 1회차 13:00-13:50 CLOSED / 2회차 14:00-14:50 CLOSED / 3회차 15:00-15:50 OPEN ...
지난 1회차 예약 → 400 "8월 20일 목요일 1회차는 이미 종료된 회차입니다."
```

## 10. 완독 후 재제출 시 모순된 채점 응답

**심각도**: 중간

### 재현 (수정 전)

이미 완독한 책에 존재하지 않는 문항번호 1개만 보내면:

```json
{"passed": true, "grade": "KING", "correctCount": 0, "totalCount": 12, "alreadyCompleted": true}
```

완독한 책은 채점을 건너뛰고 통과로 응답하는데, `correctCount`에는 이번 제출분의 즉석 채점값(0)이 그대로 나갔다. 화면이 이 값을 그리면 "0점 KING"이 된다.

### 수정

재제출은 채점 결과를 갱신하지 않으므로(`updateRecommendResult`를 타지 않는다), 점수도 **완독 당시 기록**을 돌려주는 것이 맞다. `findRecommendLogStatus`가 `correct_count`/`total_count`를 함께 읽도록 하고, DONE 분기에서 그 값으로 응답을 채운다. 옛 기록이 비어 있으면 이번 값을 유지한다.

### 검증

```
완독 후 위조 재제출 → correct=12/12 passed=true grade=KING alreadyCompleted=true
```

## 13. 위조 authToken 승인 요청이 500

**심각도**: 경미

### 정정

1차 리포트에서 "클라이언트 입력 오류인데 500"이라고 적었는데, 정확히는 **해당 catch 블록이 원래 통신 실패(타임아웃·연결 실패)를 위한 것**이고 그 경우 500은 올바르다. 문제는 PG가 4xx로 확정 거절한 경우까지 같은 취급을 받는다는 점이었다.

### 수정

`approveCallFailure(e)` 헬퍼를 추가해 `HttpClientErrorException`(PG의 확정 거절 — 재시도해도 결과가 같다)만 400으로 내리고, 그 외(타임아웃·5xx·연결 실패)는 기존대로 500을 유지한다. 망취소·실패 확정 처리는 호출부에서 그대로 수행한 뒤 분류만 한다. 단건/모바일/그룹 승인 세 경로에 동일 적용.

```
approve(위조 authToken) → 400 "결제 승인 요청이 거부되었습니다."   (수정 전: 500)
approve(악성 authUrl)   → 400 "허용되지 않은 결제 주소입니다."      (SSRF 방어 회귀 정상)
```

```

```

## 결정: 4·15번은 잡지 않는다 (2026-08-20)

둘은 뿌리가 같다 — **학생 신원이 appId 하나뿐인데 그 값이 비밀이 아니다.** 학생증에 인쇄돼 있고, 카드를 두고 온 학생은 직접 입력해서 들어간다. 비밀이 아닌 값으로는 본인 확인이 원리적으로 불가능하므로, 조건문 하나로 막을 수 있는 문제가 아니다.

닫으려면 "이 요청이 센터 기기에서 왔다"를 서버가 증명하게 만들어야 하고, 방법은 둘뿐이었다.

| | 기기 토큰 | 직원 계정 로그인 |
|---|---|---|
| 새 개념 | 토큰 테이블 1개 | 없음(기존 로그인 재사용) |
| 화면 | 2개 필요(발급·등록) | 0개 |
| 공용기기에 관리자 세션 | 없음 | 상주 → KIOSK 역할 필요 |
| 재로그인 | 없음(쿠키 1년) | 매일 |

기기 토큰 방식은 백엔드까지 구현해 전 과정을 검증했으나(등록/차단/교차센터/폐기), **운영 방식을 바꾸는 비용 대비 우선순위가 낮다고 판단해 되돌렸다.** 다른 미착수 기능이 더 급하다.

- 강제 퇴실은 가능하나 이용권은 안 깎이고 재입실도 자유로워 피해가 데이터 오염 수준이다(4번)

**재검토 트리거**: 학부모 민원이나 실제 오용이 보고되면, 또는 오픈 후 여유가 생기면 위 표에서 하나를 골라 진행한다. 그때 가장 싼 부분 조치는 appId 시도에 대한 속도 제한이다.

## 테스트 편의성 이슈

DAE001에는 운영 스케줄이 아예 없어 예약 자체가 불가능한 상태였다(테스트 중 관리자 API로 생성함). 또한 테스트 학생에게 이용권을 부여할 관리자 경로가 없어 결제 이후 구간을 특정 센터로 검증할 수 없다. `data.sql`에 센터별 기본 스케줄과 테스트 이용권을 시딩해두면 회귀 테스트가 쉬워진다.

## 개발 환경 주의 — 리소스 변경이 반영되지 않는 문제

2차 수정 중에 발견했다. IDE로 앱을 띄우면 **Java는 증분 컴파일되어 바로 반영되는데 `src/main/resources`는 동기화되지 않는다.** 실행 중인 프로세스는 `build/resources/main`을 클래스패스로 쓰는데, 이 사본이 최초 기동 시각 그대로 남아 있었다.

그래서 매퍼 XML·`schema.sql`·정적 JS를 고쳐도 **아무 반영이 없고, 에러도 안 난다** — 코드가 반영된 것처럼 보여서 원인을 찾기 어렵다.

- 증상 예: `schema.sql`에 컬럼을 추가했는데 재기동해도 DB에 그 컬럼이 안 생김
- 해결: `./gradlew processResources`로 사본을 동기화(devtools가 감지해 재기동한다)
- 확인: `stat -f "%Sm" build/resources/main/db/schema.sql`로 사본 시각을 원본과 비교

## 남은 테스트 데이터 (dev DB)

PUS002 예약 다수(8/20 및 8/21), 독서일지 1건, 입실 세션 1건, 완독 기록 1건(PUS002T04 / content_id=5). `erp_bookstore_reservation` / `reservation_log` / `slot_instance`는 앱 재기동 시 리셋된다.

`slot_instance`가 리셋되면 슬롯이 비어 예약 테스트를 못 하는데, 운영 스케줄 화면에서 주간 스케줄을 그대로 다시 저장하면 `ScheduleMaterializer`가 다시 찍어낸다.
