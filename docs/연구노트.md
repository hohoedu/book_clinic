## 2. 학생 클리닉 핵심 로직 (2026-07-09 ~ 07-10, 전면 재설계)

기존에 구현했던 레벨/EXP/뱃지/문제풀이 채점 시스템이 실사용 중 추천 로직부터 꼬여있다고 판단되어, 학생 관련 로직을 DB 스키마까지 전부 초기화하고 재설계함.

진행 순서: **① 책 추천 → ② 문제풀이/채점 → ③ 보상 지급**

### 2-1. 책 추천 (1단계, 구현 완료)
- **로그인 분기 없음**: 로그인 화면 하나, "다른 책 추천" 기능 자체를 제거(재고 누수 문제로 폐기).
- 흐름: 로그인 → `/student/main` 진입 시 `POST /clinic/recommend` 자동 1회 호출 → 로그아웃 → (오프라인 독서) → 재로그인 → "문제 풀기" 버튼 → `/student/question`.
- 추천 규칙(`ClinicService.pickWithFallback`):
  1. `erp_bookstore_priority.sort_order` 순 스캔
  2. 학생 소속 센터에 대여 가능 재고 있는 책만
  3. 직전 추천 도서와 분류(content_type)·장르(genre)가 모두 같으면 제외(dedup)
  4. 3의 조건으로 후보가 없으면 dedup 없이 재시도
  5. 그래도 없으면 한 단계 위 학년부터 순차 시도(중등 07까지 상한)
- "이미 추천받은 책" 판정은 `erp_bookstore_recommend_log`의 학생-도서 조합 존재 여부.
- 2단계 구현 후 `status`(PENDING/DONE) 개념이 생기면서 규칙 3~5가 실제로 살아있는 코드가 됨(완독 후 재추천 시 dedup 실전 검증 완료).

### 2-2. 문제풀이/채점 (2단계, 구현 완료)
- 등급 기준(합격선 = 전체문항 × 2/3 올림): 12문항 기준 12/12=독서왕, 8~11=독서친구, 8미만=재도전. 15문항도 동일 비율.
- "메인으로" 이동 시: 합격(DONE) → 다음 로그인 시 새 책 추천 / 재도전(PENDING 유지) → 재로그인해도 같은 책.
- **정답 서버 검증 전환**(2026-07-09): 클라이언트가 계산한 correctCount를 그대로 믿던 방식에서, 문항별 선택 답안만 전송받아 서버가 `itempool.ans`와 직접 대조하는 방식으로 변경. devtools 조작 방어 확인됨.
  - 잔여 한계: `/question/search` 응답이 여전히 `ans`를 노출해 네트워크 탭으로 정답 확인 가능 — 별도 작업 필요(미착수).
- 🐛 **PWA 서비스워커 캐싱 버그**(발견+수정, 2026-07-09): `sw.js`가 `/js/**`, `/css/**`를 cache-first로 캐싱해 예전 버전 JS가 계속 재생되던 문제. network-first로 전략 변경 + CACHE_NAME v2→v3로 강제 무효화.
- 미비점(미착수): 심화문제(qlevel=02) 완료 기록 DB/API 없음, 심화문제 시드 데이터 없음.

### 2-3. 레벨/뱃지/보상 재편 (2026-07-27, 3단계)
초안(레벨 1~30, 누적 EXP)은 아래 내용으로 완전히 대체됨.

**뱃지**: 22종 → 5종으로 축소. 책(클리닉)마다 · 등급형 배타 · 첫 시도 결과 기준.
- 기본 첫 시도: 불합격→참 잘했어요(재도전 고정) / 합격→독서친구 / 만점→독서왕
- 심화 첫 시도: 합격→심화 완료 / 만점→심화왕 / 불합격→없음

**레벨**: EXP 완전 폐지. 단계=학생 학년(01~06), 각 단계 레벨 1~12.
- 레벨 = min(12, ⌊학년별 완독 권수 ÷ 학년별 필요권수⌋ + 1), 매번 재계산(저장 안 함).
- 학년별 필요권수: 초1·2=8, 초3=5, 초4~6=4.
- 테이블은 최종적으로 `erp_bookstore_level`(칭호)만 유지, 레벨 규칙(단계명/특징/필요권수)은 DB가 아니라 `ClinicService.LEVEL_RULES` Java 상수로 전환(2026-07-28) — 어드민 편집 화면이 없고 data.sql도 매기동 리셋이라 DB에 둘 실익이 없었음.

**보상 테이블 최종 4개**: level(칭호) / badge(마스터) / student_badge(이력) / student_card(이력).

### 2-4. 온라인 카드 수집 기능 (2026-07-27 구현, 07-28 재작업)
- 카드 2종: NORMAL(완독한 책마다 1장, 책당 고정) / RARE(NORMAL 10장마다 추가).
- 10장(NORMAL 기준) = 오프라인 실물 1장. 시스템은 진행도+달성 표시까지만, 실물 지급/소모는 오프라인 수동.
- 저장: `erp_bookstore_student_card` (id surrogate PK, 필터드 유니크 인덱스 2개로 DB단 중복지급 방지).
- 미착수: 독서여권·독서탐험 결과화면 칸은 여전히 더미 placeholder.

### 2-5. 보류/미결정 항목
- **실물 도서 반납 시점**: 지금은 추천=대여만 있고 반납 로직이 없어 재고가 계속 마모됨. 후보: 문제풀이 완료 시 자동 반납 vs 센터 수동 반납 UI. → 2026-08-07 작업 항목으로 재부상(§4 참고).
- 동시 요청(레이스 컨디션) UX: 데이터 정합성은 안전하나, 나중 요청이 그냥 에러로 끝남(합류 로직 없음) — 우선순위 낮은 개선 후보.
- 학생 status_key / 센터 status 필터링이 추천 로직에 전혀 없음 — 퇴원/휴업 기능이 생기기 전까지는 영향 없음.

## 3. 인프라·데이터 구조 관련 결정

### 3-1. DB 시딩 구조
- `content`/`item`/`itempool`/`center` 관련 테이블은 자동 리셋 제외 — `data-books.sql`/`data-itempool.sql`을 DBeaver로 최초 1회 수동 실행해야 함.
- `erp_bookstore_item`은 2026-07-14부터 다시 매 기동 리셋 대상(재고/대여상태가 영구히 쌓이는 버그 때문).
- 나머지(`erp_user`/`erp_student`/뱃지/레벨/데모 학생 등)는 `data.sql`로 매번 리셋.

### 3-2. bcode(도서 식별자) UUID vs ISBN
- 원래 실제 ISBN이었으나 커밋 `2bc0e05`에서 서버 발급 숫자형 UUID로 변경됨(오타 리스크 때문).
- 사용자는 **ISBN 복원을 원함** — 중복 등록 판별, 실물 바코드 스캔 연동, 외부 도서 API 조회, 체크섬 검증이 UUID로는 불가능하다는 근거. 아직 논의/구현 미착수.

### 3-3. 시간대(KST) 규칙
- 모든 시간/날짜는 KST 기준. SQL에서 `GETDATE()` 금지, `DATEADD(HOUR, 9, GETUTCDATE())` 사용. (2026-07-28 예약 시딩 버그로 확정)

### 3-4. Firestore 직렬화 주의
- `java.time`(LocalDateTime 등) 필드를 가진 POJO를 그대로 Firestore에 넣으면 `InaccessibleObjectException`으로 터짐. 반드시 Map으로 flatten(`.toString()` ISO 변환 등). 2026-07-24 실시간 모니터링 푸시 전면 장애 원인 중 하나였음.

### 3-5. 컬럼 크기 원칙
- VARCHAR를 넉넉하게 잡지 말고 실제 값 크기에 맞춤. 선택지가 2개면 BIT.

## 7. 도메인별 패키지 구조 점검 (2026-08-19)

- 사용자가 "프로젝트가 정리가 안 된 느낌"이라며 도메인별로 정리하는 작업의 명칭을 문의함. 실제 착수 요청은 아니고 용어 확인 및 현황 점검 목적.
- 용어 정리: 이런 작업은 통상 **도메인 기반 리팩토링(Domain-Driven Refactoring)** 또는 **package-by-feature 리팩토링**이라 부름. DDD는 더 넓은 개념(바운디드 컨텍스트 설계까지 포함)이라 지금 상황엔 과한 표현.
- 현재 구조 재확인 결과: `src/main/java/com/hohoedu/book_clinic` 하위가 이미 `student`/`clinic`/`book`/`question`/`priority`/`monitor`/`diary`/`reservation`/`payment`/`pass`/`user`/`schedule`/`common`/`_core`로 도메인별 분리되어 있고, 각 도메인 내부는 Controller→Service→Repository 3계층 반복 구조(1장 설계 원칙 그대로 유지됨, `연구노트_60장.md` 1장 참고).
- 결론: **패키지 구조 자체는 이미 도메인 기준으로 정리되어 있어 즉시 재작업이 필요한 상태는 아님.** "정리 안 된 느낌"의 원인은 구조보다는 개별 도메인 내부의 일관성(파일 개수 편차, DTO/네이밍 컨벤션 편차 등)일 가능성이 높음 — 다음에 이 주제가 다시 나오면 패키지 재배치가 아니라 도메인별 내부 일관성 점검부터 제안할 것.
- 액션 아이템 없음(보류). 사용자가 구체적으로 어떤 부분이 불편한지(파일 찾기 어려움/네이밍 혼란/응집도 등) 짚어주면 그때 범위를 좁혀 착수.
