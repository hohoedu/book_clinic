# 자동결제(정기결제) 전환 설계 — 2026-09-07

## 무엇을 바꾸나

지금은 학부모가 매달 앱에서 이니시스 표준결제창으로 **일시불 1회씩** 직접 결제한다
(빌키 없음, 할부 없음 — `ddl-payment.sql` 상단 주석 참고). 이걸 **카드 1회 등록 후
매월 자동 청구**되는 구독으로 바꾼다. 확정된 방향은 넷이다.

| 항목 | 결정 |
|---|---|
| 결제수단 | KG이니시스 빌키(정기결제). 빌링 전용 MID로 카드등록 결제창 → `CARD_BillKey` 저장 → 매월 빌링 승인 API |
| 전환 범위 | **전면 전환**. 앱의 신규 결제 경로는 카드등록·자동결제만 남는다. 기존 일시불 코드는 과거 내역 조회/환불용으로만 유지 |
| 결제 주기 | **학생(구독)별 앵커일** — 최초 결제일의 일자에 매월 청구 |
| 이용권 주기 | **결제일 기준 1개월** (3/15 결제 → 3/15~4/14 유효). 달력 월 단위 폐기 |
| 형제 | 카드 1장에 형제 합산 **승인 1건**, 학생별 payment 행 분리(기존 `group_order_no` 구조 유지) |

## 이 전환이 건드리는 기존 전제

이용권을 달력 월에서 앵커 주기로 옮기는 것이 이번 작업에서 가장 파급이 큰 부분이다.
아래 네 곳이 "한 달 = 1일~말일"을 전제로 짜여 있다.

1. **이용권 발급** — `PassService.grant()`가 `billingYm`으로 `valid_from`=1일,
   `valid_until`=말일을 역산한다. 앵커 주기에서는 호출부가 기간을 직접 넘겨야 한다.
2. **월 예약 상한** — `PassService.monthlyCapacity()` / `PassMapper.sumMonthlyTotalCount`가
   달력 월과 겹치는 이용권의 `total_count`를 합친다. 앵커 주기에서는 한 달에 두 주기가
   걸치므로 그대로 두면 상한이 최대 두 배가 된다. **"그 날짜를 품은 주기"** 기준으로 바꾼다.
3. **중복결제 방지 유니크** — `UX_payment_active_billing (student_id, service_code, billing_ym)`.
   앵커 주기에서는 청구월이 주기를 대표하지 못한다. `cycle_from` 기준으로 교체한다.
4. **서당 병행 학생** — `source='SEODANG'` 이용권은 여전히 달력 월(전월 20일 일괄청구)이다.
   **두 체계가 공존한다.** 그래서 pass에서 달력 월 개념을 지우지 않고, 주기를 표현하는
   `valid_from`/`valid_until`을 단일 진실로 삼는다 — 서당분은 1일~말일이 그대로 하나의 주기가
   되므로 조회 쿼리는 한 벌로 유지된다. `billing_ym`은 정산 대조용 라벨로만 남는다
   (PG 자동결제분은 `cycle_from`이 속한 달을 적는다).

## 흐름

### 1. 카드등록(빌키 발급)
**모바일 빌키발급 모듈**(`mo-bill`)로 띄운다. 처음에는 PC 웹표준의
`acceptmethod=BILLAUTH(Card)` 방식으로 구현했다가 바꿨다 — 이 프로젝트의 결제창은 이미
모바일 모듈을 쓰고 있고(PC의 `window.open`을 webview_flutter가 지원하지 않아서),
빌키 발급도 같은 제약을 받기 때문이다. 모바일 빌링은 일반 모바일 결제창과도 요청 URL과
파라미터가 다른 별도 모듈이다.

인증 결과(`P_REQ_URL`)를 빌링 MID로 승인하면 빌키가 돌아온다. 이 단계는 **돈이 빠지지 않는다.**
모바일 모듈에는 PC의 `signature`/`mKey` 같은 서명 파라미터가 없어서, 등록 확정은 우리가
`P_NOTI`로 실어 보낸 등록 주문번호로 구독을 되짚어 처리한다(일반 결제창과 같은 구조).

### 2. 최초 청구(등록 직후 즉시)
발급된 빌키로 곧바로 빌링 승인 1건을 낸다. 이 날짜가 앵커일이 되고,
이용권은 `오늘 ~ 한 달 뒤 전일`로 발급된다.

### 3. 매월 재청구 — `SubscriptionBillingJob`
매일 03:20 KST, `status='ACTIVE' AND next_billing_on <= 오늘`인 구독을 훑는다.
멤버 금액을 합산해 승인 1건 → 학생별 payment 행 + 이용권 발급 → `next_billing_on`을
앵커 기준 다음 달로 민다. 앵커일이 그 달에 없으면(31일 앵커, 2월) 말일로 당기되
**앵커 자체는 보존**한다(3월에 다시 31일로 돌아온다).

실패는 D+1, D+3, D+5로 3회 재시도하고 그래도 실패하면 `PAUSED` + 알림.
`PAUSED`는 이용권을 회수하지 않는다 — 이미 쓴 주기는 정당하게 결제된 것이고,
다음 주기가 안 열릴 뿐이다.

### 4. 해지 / 카드 변경
해지는 `CANCELED`로 내리고 이미 발급된 이용권은 그 주기 끝까지 살려둔다(중도 환불은
기존 환불 규정 그대로 `PaymentService.refund()`를 탄다). 카드 변경은 새 빌키를 받아
같은 구독의 `bill_key`를 교체하며, 앵커일과 주기는 유지한다.

## 멱등성 — 자동결제에서 제일 중요한 지점

배치가 두 번 돌거나(재기동, 중복 인스턴스) 승인 응답을 못 받고 타임아웃 나면 이중 청구가 된다.
막는 장치를 세 겹으로 둔다.

1. `next_billing_on`을 조건부 UPDATE로 **먼저 선점**한다(WHERE next_billing_on = 읽은 값).
   0행이면 다른 인스턴스가 가져간 것이므로 건너뛴다 — 환불의 `claimRefund`와 같은 방식이다.
2. `moid`(주문번호)에 주기를 넣어 결정적으로 만든다: `SUB{subscriptionId}-{cycleFrom}`.
   같은 주기를 다시 청구하면 이니시스가 중복 주문번호로 거절한다.
3. DB 유니크 `(student_id, service_code, cycle_from)`이 최종 방어선.

승인 응답을 못 받은 건은 **실패로 단정하지 않는다.** 기존 일시불과 같은 원칙으로,
거래조회(`v2/pg/inquiry`)로 실제 승인 여부를 확인한 뒤 확정하거나 `needs_review`를 세운다.

## 미확정 / 실 MID 발급 시 확인할 것

- **빌링 전용 실 MID·`billing-api-key`** — 지금은 테스트 MID `INIBillTst`로 설정만 잡아뒀다.
- **모바일 빌키발급 폼 파라미터와 요청 URL** — `manual.inicis.com/mobile/mo-bill.html`이 공개
  접근에서 리다이렉트돼 확인하지 못했다. `billing-mobile-url`은 설정으로 빼뒀고 폼 필드는
  일반 모바일 결제창 규격을 따라 두었으니, 매뉴얼 배포본과 대조해 맞춰야 한다.
- **빌키 응답 필드명** — `P_BILLKEY` / `CARD_BillKey` / `P_CARD_BILLKEY` 후보를 순서대로 보고 있다.
  실제 응답을 확인해 하나로 좁힌다.
- **빌링 승인 API의 성공 코드와 금액 필드** — `resultCode="00"` + `tid` 존재로 판정하고 금액은
  `price`/`TotPrice`를 함께 본다. 매뉴얼 대조 필요.
- 결제 실패 시 학부모 알림 채널(푸시/문자) — 지금은 로그와 앱 상태 화면(PAUSED + 사유)뿐이다.
- 서당 병행 학생이 자동결제로 넘어올 때의 이관 절차.
