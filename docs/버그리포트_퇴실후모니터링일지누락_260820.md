# 버그 리포트: 퇴실 후 실시간 모니터링/독서일지 누락 및 이용완료 중복 생성

- 작성일: 2026-08-20
- 심각도: 치명적 (Critical) — 학생 이용 기록 유실 및 중복 데이터 발생
- 상태: 원인 규명 완료, 1차 수정 반영(코드 추적으로 검증 / 실행 테스트 아직 안 함), 부가 이슈는 보류

## 재현 절차

1. 결제 → 예약 → 문제풀이(quiz/submit) → 풀이 후 퇴실까지 정상 진행
2. 퇴실 처리 시점 이후
   - 실시간 모니터링 화면에서 해당 학생이 사라짐
   - 독서일지 화면에도 해당 기록이 나타나지 않음
3. 같은 날 앱에서 "이용취소" 후 재예약 진행
   - 모니터링 / 독서일지에 다시 정상적으로 나타남
4. 재예약 상태에서 문제풀이 앱에 다시 로그인하여 재제출
   - "이용완료"가 2건으로 중복 생성됨
   - 이 시점에 모니터링 / 독서일지가 다시 사라짐

## 기대 동작

- 퇴실 이후에도 해당 학생의 당일 이용 기록은 모니터링(이력) 및 독서일지에 계속 남아야 함
- 재예약/재제출 시 "이용완료" 상태가 중복 생성되지 않고 기존 기록이 갱신되어야 함

## 실제 동작

- 퇴실 처리 후 모니터링/독서일지에서 기록이 사라짐
- 이용취소 → 재예약 시에는 다시 나타났다가, 재제출 시 이용완료 2건 중복 생성 + 모니터링/독서일지 재차 누락

## 영향도

- 학생의 실제 이용 이력(독서일지)이 소실되어 학부모/센터 대상 데이터 신뢰도에 직접 영향
- 이용완료 중복 건으로 인해 통계/카운트(레벨, 리워드 등 완독 파생 데이터 포함 가능) 오염 가능성

## 원인 분석

버그의 근본 원인은 **"실시간 모니터링"과 "독서일지" 두 화면이 모두 `erp_bookstore_reservation.status = 'RESERVED'`를 목록의 루트 필터로 쓰고 있는데, 정작 학생이 정상적으로 입실하면 그 예약의 `status`가 `RESERVED → ATTENDED`로 바뀌면서 화면에서 스스로 사라진다**는 데 있음. 여기에 "ATTENDED 상태는 당일 재예약 방지 로직의 보호 대상이 아니다"는 결함이 겹치면서 "이용완료(ATTENDED)" 예약 행이 중복 생성됨.

### 1. 모니터링/독서일지 화면이 `status='RESERVED'`인 예약만 조회

- `src/main/resources/mapper/MonitorMapper.xml` `findReservationCards` (281-287행)
- `src/main/resources/mapper/DiaryMapper.xml` `findDiaryRows` (66-68행)

```sql
WHERE si.service_date = #{date}
  AND si.center_code = #{centerCode}
  AND r.status = 'RESERVED'
```

세션/독서일지는 `OUTER APPLY`로 예약 행 위에 얹는 구조라, 루트가 되는 예약 행이 `RESERVED`가 아니면 학생이 통째로 목록에서 빠짐.

### 2. 입실하면 예약이 `ATTENDED`로 바뀌고, 다시는 `RESERVED`로 돌아오지 않음

- `MonitorService.enterSession()` (56-75행) → `reservationService.markAttended(studentId, today)`
- `ReservationService.markAttended()` (112-122행) → `repository.transitionStatus(reservationId, "RESERVED", "ATTENDED")`

퇴실 처리(`exitSession`)는 예약 테이블을 건드리지 않으므로, **정상적으로 등원해서 문제까지 다 풀고 퇴실한 케이스가 그대로 "모니터링/독서일지에서 사라지는" 케이스**가 됨. (`reservation.js`: `RESERVED`="예약 완료", `ATTENDED`="이용 완료")

### 3. "이용취소 후 재예약"이 통과되는 이유

- 취소(`ReservationRepository.cancelReservation`, `ReservationMapper.xml` 123-131행)는 `WHERE status='RESERVED'`만 갱신 → 이미 `ATTENDED`인 예약은 취소가 실패함(`Exception400`).
- 하지만 당일 중복예약 방지 로직도 전부 `status='RESERVED'`만 검사함:
  - `ReservationService.reserveOne()` (292-323행) 의 `countOtherReservedOnDate`
  - `ReservationRepository.countOtherReservedOnDate` (`ReservationMapper.xml` 81-89행)
  - 필터드 유니크 인덱스: `UX_reservation_slot_student ... WHERE status = 'RESERVED'` (`schema.sql`/`ddl-schedule.sql` 269-271행)

이미 `ATTENDED`로 바뀐 예약은 이 방어선들에 걸리지 않으므로, 같은 학생이 같은 날 새 `RESERVED` 예약 행을 하나 더 만들 수 있고, 이 새 행이 1)의 필터를 통과해 화면에 "다시 나타남".

### 4. 재로그인 시 "이용완료" 2건 중복 생성 지점

재예약으로 생긴 새 `RESERVED` 행에서 문제풀이 앱에 재로그인하면 `MonitorService.enterSession → reservationService.markAttended`가 다시 호출됨. `findReservedReservationIdByStudentAndDate`(`ReservationMapper.xml` 226-234행, `TOP 1 ... WHERE status='RESERVED'`)로 찾은 **새 예약 행만** `ATTENDED`로 전이 → 그날 그 학생에 대해 `ATTENDED` 상태 행이 **2건**(최초 방문분 + 재예약분) 남음. 관리자 "예약 현황" 화면에서 "이용완료" 2건으로 보이는 원인. 이 새 행도 곧바로 `RESERVED`에서 벗어나므로 다시 필터에 걸려 모니터링/독서일지에서 두 번째로 사라짐(시나리오 5단계와 일치).

### 5. 부가 요인 — 세션/독서일지 1:1 구조

- `erp_bookstore_clinic_session`에 `(student_id, session_date)` 유니크 제약이 없고, `enterSession()`은 `status='ENTERED'`인 세션이 없으면(이미 `EXITED`면) 새 세션을 그냥 추가함.
- `erp_bookstore_diary.session_id`는 `UNIQUE`(1세션=1일지)라 같은 날 두 번째 세션이 생기면 독서일지도 별도 행으로 새로 생김.
- 조회는 항상 `OUTER APPLY (... ORDER BY session_id DESC)`로 "최신 세션 1건"만 붙이므로, 재입실로 세션이 여러 건 생기면 이전 세션의 일지가 화면에서 조용히 묻힘.

## 가설 정리 (근본 원인 우선순위)

1. **[핵심]** 예약 상태(RESERVED→ATTENDED)를 "화면 노출 여부" 필터로 재사용한 설계 결함. 두 화면이 원하는 조건은 "오늘 그 학생에게 유효한 예약이 있었는가"(활성 상태 전체)이지 "지금 이 순간 RESERVED인가"가 아님.
2. **[연쇄]** 당일 중복예약 방지(`countOtherReservedOnDate`, 필터드 유니크 인덱스)도 `status='RESERVED'`만 검사해서, 이미 ATTENDED된 학생이 같은 날 예약을 또 만들 수 있음 → 재로그인 시 ATTENDED 2건 생성으로 이어짐.
3. **[부가]** 세션-일지 1:1 구조 + 세션 재생성 로직 때문에 같은 날 여러 세션/일지 행이 생겨, "최신 세션 1건만" 보는 조회가 예전 기록을 가릴 수 있음.

## 적용된 수정 (2026-08-20)

핵심 원인 하나로 좁혀짐: `status` 컬럼이 "화면에 보여줄지"와 "오늘 예약을 또 할 수 있는지" 두 가지 서로 다른 목적에 동시에 쓰이고 있었음. 두 목적 모두 "CANCELED만 아니면 유효"로 통일해서 수정.

| 파일 | 위치 | Before | After |
|---|---|---|---|
| `MonitorMapper.xml` | `findReservationCards` | `r.status = 'RESERVED'` | `r.status <> 'CANCELED'` |
| `DiaryMapper.xml` | `findDiaryRows` | `r.status = 'RESERVED'` | `r.status <> 'CANCELED'` |
| `ReservationMapper.xml` | `countOtherReservedOnDate` | `r.status = 'RESERVED'` | `r.status <> 'CANCELED'` |

세 곳을 세트로 바꿔야 했음 — 화면 필터만 열고 중복예약 차단을 그대로 두면, 이미 생겨버린 중복 행 때문에 화면에 카드가 두 장씩 뜨는 새 문제가 생김.

### 수정 후 흐름 재검증 (코드 추적, 실행 테스트는 미실시)

1. 결제 → 예약: `status='RESERVED'`로 생성. 이상 없음.
2. 문제풀이 앱 로그인(입실): `enterSession → markAttended`가 `RESERVED → ATTENDED` 전이. 모니터링/독서일지 필터가 `<> 'CANCELED'`로 바뀌었으므로 **계속 노출됨** (기존엔 여기서 사라졌음).
3. 퇴실: `exitSession`은 세션만 `EXITED` 처리, 예약 상태는 안 건드림. 여전히 `ATTENDED`라 계속 노출됨 — 1번 증상 해소.
4. 이용취소 시도: `cancelReservation`은 원래부터 `WHERE status='RESERVED'`만 갱신하므로 `ATTENDED` 예약은 취소가 실패함(변경 없음, 기존에도 이미 막혀 있었음).
5. 재예약 시도: `countOtherReservedOnDate`가 이제 `ATTENDED`인 기존 예약도 "이미 예약 있음"으로 집계 → `Exception400("하루에 한 회차만 예약할 수 있습니다.")`로 **재예약 자체가 차단됨** — 3·4번 증상(재예약 성공 → 이용완료 2건 → 재차 누락)의 연쇄가 원천적으로 끊김.

### 남은 사항

- **미세한 틈**: 정확히 같은 회차(slot)를 다시 예약하는 극단적 케이스는 DB 유니크 인덱스(`UX_reservation_slot_student`, `WHERE status='RESERVED'`)가 아직 `ATTENDED`를 커버하지 않음. 실사용 시나리오(다른 회차로 재예약)는 이번 수정으로 막히므로 우선순위 낮음 — 스키마 마이그레이션 필요 시 별도 진행.
- **부가 이슈(보류)**: 세션/독서일지 1:1 구조(`erp_bookstore_clinic_session`에 `(student_id, session_date)` 유니크 제약 없음) — 이번 수정으로 정상 플로우에서는 발생 조건 자체가 없어졌으나, 관리자가 수동으로 대리 예약을 추가하는 등 예외 경로는 여전히 재현 가능성 있음. 근본 수정(세션 재사용 로직 변경)은 착수하지 않음.
