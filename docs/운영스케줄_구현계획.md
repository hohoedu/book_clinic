- DB: `src/main/resources/db/ddl-schedule.sql` 설계, `schema.sql`에 반영 + 로컬 DB 11개 테이블 생성 완료
- 참고: 화면 CRUD 전체 목록은 별도 정리(claude.ai Artifact "운영 스케줄 기능 명세")

## 결정된 사항 4가지

1. 적용 시작일 + 즉시 적용 체크박스 → 저장 버튼 앞 배치 (화면 반영 완료)
2. 예외 일정 **수정 화면 없음** — 삭제 후 재등록으로 대체
3. 센터는 **로그인 직원 센터로 고정**, 센터 선택 UI 없음
4. 예약 걸린 슬롯 저장/삭제 시 **경고 + 차단** — 서버 API 붙일 때 반드시 같이 구현 (아직 미착수)

## 구현 순서 (범위 축소 없음, 8/14~8/17 3일 배정)

1. **요일별 스케줄 조회 API** — 센터 기준 요일별 최신 버전 조회 → 요일 탭 로드
2. **요일별 스케줄 저장 API** — 운영여부·운영시간·회차기본시간·최대예약인원 + 회차 목록을 적용 시작일(effective_from) 기준 upsert
   - ✅ **8/14 완료.** `schedule` 패키지(Controller/Service/Repository/dto) + `mapper/ScheduleMapper.xml` 신규.
     `GET|POST /admin/operation/schedule/week`. 센터는 로그인 유저 고정. 같은 effective_from 재저장 시
     `_del`에 UPDATE 스냅샷 남기고 덮어씀. seq는 서버가 시작시각 순으로 재부여. 예약 있는 요일은 저장
     자체를 차단(결정 4 일부 선반영).
3. **materialize() 슬롯 생성 엔진** — 요일 버전 + 예외를 합쳐 `slot_instance`를 찍어내는 핵심 로직.
   전체 작업 중 가장 무겁다. (`ddl-schedule.sql` 상단 주석의 의사코드 참고)
4. **예약 보호(경고·차단)** — 결정 4. 슬롯에 예약이 있으면 저장·삭제 자체를 막는다.
5. **예외 일정 조회·등록 API** — 기간 겹침 검증 포함, 등록 즉시 3번 엔진 재호출
6. **예외 일정 삭제 API** — 삭제 후 materialize 재계산 (수정 API는 결정 2에 따라 안 만듦)
7. **프론트 실연동** — `operation-schedule.js`를 실제 API 호출로 교체 (현재는 로컬 상태로만 동작, 새로고침하면 날아감)
8. **통합 확인** — 저장 → 슬롯 생성 → 예외 적용 → 학생 예약 화면까지 이어지는지 점검
