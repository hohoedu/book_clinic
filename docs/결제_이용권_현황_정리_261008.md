# 결제·이용권 현황 정리 — 2026-10-08

> 실결제 전환을 앞두고 결제와 이용권이 지금 어떻게 동작하는지, 무엇을 결정해야 하는지 정리한 문서입니다.
> 1~4장은 정책·현황(기획/운영 공유용), 5장 이후는 개발 참고용입니다.

## 요약

- 이용권은 **12회권(60,000원)을 사 두고, 첫 예약일부터 90일 안에 쓰는** 구조입니다.
- 지금 실제로 결제가 되는 경로는 **일시불(앱에서 매번 직접 결제)** 하나입니다.
- 자동결제(카드 등록 후 자동 청구)는 코드는 있지만 **청구가 꺼져 있습니다**(2026-09-14~). 이용권 정책과 청구 방식이 맞지 않기 때문입니다.
- 운영 서버는 아직 **이니시스 테스트 상점**으로 연결되어 있어 실제 돈이 오가지 않습니다.
- 실결제 전환 전에 **자동결제를 어떻게 할지**(5장 "결정 필요")를 먼저 정해야 합니다.

## 2. 이용권 규칙

| 항목 | 규칙 |
|---|---|
| 지급 | 결제가 승인되면 12회 지급. 이때는 유효기간이 정해지지 않음 |
| 유효기간 | 그 이용권으로 **처음 예약한 회차 날짜부터 90일** |
| 차감 | **예약할 때 1회** 차감 (입실 시 차감 아님) |
| 여러 장 보유 시 | 먼저 만료되는 이용권부터 사용, 아직 안 쓴 이용권은 마지막 |
| 예약 취소 | 취소하면 1회 복구. 학생·학부모는 **회차 시작 24시간 전까지**, 센터 직원은 당일도 가능 |
| 첫 예약 취소 | 그 이용권 사용 이력이 0이 되면 유효기간도 다시 풀림 (90일이 다시 시작 전 상태로) |
| 노쇼 | 복구 없음 (1회 소멸) |
| 만료 | 90일이 지나면 남은 횟수가 있어도 사용 불가, 이월 없음 |
| 예약 한도 | 남은 횟수만큼 예약 가능, 하루 최대 4회차 |
| 재구매 | 같은 달에 여러 번 구매 가능 |

**서당 일괄청구 학생**은 예외로, 여전히 **달력 월(1일~말일)** 단위 이용권을 받습니다. 두 방식이 함께 운영됩니다.

## 3. 환불 규정

결제 후 경과일은 보지 않고 **사용 횟수**만 봅니다.

| 사용 횟수 | 환불 |
|---|---|
| 0회 | 100% |
| 1회 | 75% |
| 2회 | 50% |
| 3회 이상 | 환불 불가 |

> ⚠️ 이 규정은 월 4회·8회권 시절 기준입니다. **12회권에도 그대로 적용할지 재검토가 필요합니다.**

- 앱에서 신청하면 규정이 자동 적용되고 카드 취소까지 바로 진행됩니다.
- 환불되면 그 이용권의 남은 횟수는 회수됩니다.
- 형제를 한 번에 결제한 경우에도 학생별로 나눠 환불할 수 있습니다.

## 5. 결정 필요 — 자동결제를 어떻게 할 것인가

이용권은 "필요할 때 사 두는 12회 묶음"으로 바뀌었는데, 자동결제는 "매달 같은 날짜에 청구"로 설계되어 있습니다. 매달 청구를 켜면 **다 쓰지 않은 달에도 60,000원이 결제되고 이용권이 계속 쌓입니다.** 그래서 지금은 꺼 둔 상태입니다.

| 선택지 | 내용 | 장단점 |
|---|---|---|
| **A. 일시불만으로 오픈** | 자동결제는 접어 두고 현재 일시불로 실결제 시작 | 가장 빠름. 학부모가 매번 직접 결제해야 함 |
| **B. 잔여 2회 이하일 때 자동충전** | 남은 횟수가 2회 이하가 되면 12회권 자동 결제 | 정책과 맞음. 개발 추가 필요(아래 결정사항 포함) |
| C. 매달 같은 날짜 청구 | 기존 설계 그대로 켜기 | 이용권 정책과 충돌 — 권장하지 않음 |

B를 택할 경우 정해야 할 것:

1. 충전 시점 — 잔여가 2회가 되는 즉시 / 하루 한 번 모아서
2. 형제 묶음 — 한 명이라도 2회 이하면 형제 전원 충전? 해당 학생만?
3. 결제 실패 시 — 재시도 횟수, 몇 번 실패하면 자동결제 중지

## 6. 그 밖의 미정 정책

`docs/결제_정책_결정사항.csv` 기준으로 아직 정해지지 않은 항목입니다.

- 학원비 결제 채널 (앱 결제 / 책방 자체 수납)

- 월 중간 등록자 첫 결제 금액, 29~31일 결제일 처리 (자동결제 방식이 B로 가면 필요 없어질 수 있음)
- 해지 — 신청 채널, 해지 시점, 남은 횟수 처리
- 환불 — 처리 흐름(자동 / 승인 후), 학원비 환불과 연동 여부, 관리자 웹 기능 위치
- 학원비 수기 결제 허용 여부
- 결제 알림(알림톡) 도입 여부

※ "회차 차감 시점"은 **예약 시 차감**으로 이미 확정되었습니다(CSV 미반영).

## 8. (개발) 구조

### 테이블

| 테이블 | 역할 |
|---|---|
| `erp_bookstore_product` | 상품 (횟수, 가격, 판매 여부) |
| `erp_bookstore_pass` | 이용권. 결제 1건 = 1행. `valid_from/valid_until`이 NULL이면 아직 기간 미정 |
| `erp_bookstore_pass_use` | 차감 이력. 1행 = 1회. 취소 시 행을 지우지 않고 `canceled_at`만 채움 |
| `erp_bookstore_payment` | 결제. 상태 READY / PAID / CLOSED(결제 전 이탈) / FAILED / CANCELED |
| `erp_bookstore_payment_cancel` | 환불 이력 (적용 규정, 사용 일수·횟수 스냅샷) |
| `erp_bookstore_payment_log` | 이니시스 요청·응답 로그 (마스킹) |
| `erp_bookstore_refund_rule` | 환불 규정. 수정하지 않고 비활성화 후 새 행 추가 |
| `erp_bookstore_subscription` | 자동결제 구독 (카드 1장 단위, 빌키 보관) |
| `erp_bookstore_subscription_member` | 구독에 묶인 학생 |

불변식: `pass.total_count − pass.remain_count = 취소되지 않은 pass_use 행 수`. 환불 계산이 이 값을 씁니다.

### 결제 흐름 (일시불)

1. 앱 → `/payment/checkout` (형제는 `/checkout/select` → `/checkout/group`) → 결제 READY 생성
2. 이니시스 결제창 인증 → `/payment/return` → 서버가 승인 요청
3. 금액 대조 → PAID → `PassService.grantUnassigned`로 12회 지급 → `/payment/done`
4. 형제 묶음은 이니시스에 1건으로 승인하고, 학생별 결제 행은 `group_order_no`로 묶음
5. 금액 불일치처럼 자동으로 끝내지 못한 건은 `needs_review`가 켜져 "결제 이상 건" 화면에 표시

### 자동결제 흐름 (현재 청구 꺼짐)

1. `/payment/billing/checkout?firstBillingOn=` → 이니시스 모바일 빌키 발급창 (현재 금액 0원)
2. `/payment/billing/return` → `SubscriptionService.completeBillKeyReg()` → 구독 ACTIVE
3. 매월 청구 `SubscriptionBillingJob.chargeDueSubscriptions` — `MONTHLY_BILLING_ENABLED = false`로 잠금
4. 이중 청구 방지: ① 다음 청구일 조건부 UPDATE로 선점 ② 주문번호 `SUB{id}-{cycleFrom}` 고정 ③ DB 유니크 `(student_id, service_code, cycle_from)`
   — 셋 다 날짜(주기) 기준이라, 잔여 기반 충전(B안)으로 가면 다시 설계해야 함
