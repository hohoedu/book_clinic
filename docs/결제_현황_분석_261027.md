## 0. 한 줄 요약

- 현재 실제로 돈이 오가는 경로는 **앱 일시불 결제 하나**다 (KG이니시스 모바일 결제창, 카드, 일시불).
- 상품은 **독서 클리닉 12회권 60,000원** 하나다.
- 결제가 승인되면 **사용기한이 정해지지 않은 12회 이용권**이 생기고, **첫 예약 회차 날짜부터 90일**이 시작된다.
- 이용권은 **예약할 때 1회 차감**, 회차 24시간 전까지 **취소하면 복구**된다. 입실·노쇼는 횟수에 영향이 없다.
- 환불은 **결제일 + 3개월 이내, 남은 횟수 × 3,000원, 1회만**, 앱에서 신청하면 바로 PG 취소까지 간다.
- 자동결제(빌키 구독)는 코드가 있지만 **2026-09-14부터 청구가 잠겨 있다** (잔여 2회 트리거 미구현).

### 1-2. 설계 원칙 (코드 주석에 명시된 것)

1. **금액은 서버가 정한다** — 어떤 API도 금액을 입력으로 받지 않는다. 결제 금액은 product, 환불 금액은 서버 계산.
2. **결제창은 서버가 렌더링** — signKey를 앱에 넣지 않기 위해. 앱은 URL만 연다.
3. **READY 선기록** — 결제창을 띄우기 전에 payment 행을 만든다. 이탈 건도 정산 대조가 되도록.
4. **이중 금액 검증** — 인증 금액(P_AMT)이 다르면 승인 요청 자체를 안 보내고, 승인 응답 금액도 다시 대조한다.
5. **HTTP와 트랜잭션 분리** — PG 호출(최대 15초)을 트랜잭션 밖에 두고, DB 확정은 `*TxService`가 짧게.
6. **돈과 이용권은 한 트랜잭션** — `confirmPaid`(PAID + 이용권 발급), `confirmRefunded`(환불액 + 이용권 회수).
7. **PG 통신 원문 전부 저장** — `payment_log`에 카드번호 마스킹 후 저장.
8. **콜백 URL 검증** — `P_REQ_URL` 등은 `https://*.inicis.com`만 허용.
9. **콜백은 세션 없음** — 이니시스발 cross-site POST라 쿠키가 안 온다. 주문번호로 결제 행을 찾는다.
10. **자동으로 못 끝낸 건은 사람에게** — `needs_review` 플래그 → 관리자 "결제 이상 건" 화면.

### 2-1. 단건 결제

| # | 주체 | 동작 | 코드 |
|---|---|---|---|
| 1 | 앱 | WebView로 `GET /payment/checkout?productCode=BOOK_12` (세션 쿠키 필요) | `PaymentCheckoutViewController.checkout` |
| 2 | 서버 | 형제 그룹이 2명 이상이면 형제 선택 화면으로 redirect, 아니면 `prepare()` | |
| 3 | 서버 | 판매중 상품 조회 → 같은 학생·서비스의 READY가 있으면 **재사용** → 없으면 `order_no = BC + yyyyMMddHHmmss + 난수6` 발급 | `PaymentService.prepare` |

| 9 | 서버→이니시스 | `approveMobile(P_REQ_URL, P_TID)` = **실제 승인** → `payment_log(APPROVE)` | `InicisClient.approveMobile` |

- **이탈**: 결제창 X/뒤로가기 → `/payment/abandon` 또는 `closeUrl` → `CLOSED`.
- **콜백 유실**: `PaymentCleanupJob`이 5분마다 READY 10분 초과 건을 이니시스 거래조회로 확인해, 실제 승인됐으면 PAID + 이용권으로 복구, 아니면 CLOSED. 최근 2시간 CLOSED도 재확인(배치가 닫은 직후 사용자가 승인한 레이스).

### 2-2. 형제 묶음 결제

- 형제 관계는 `erp_student_sibling`에 **사람이 직접 INSERT** (자동 매칭 없음).
- `prepareGroup()`: 선택 학생 전원 형제 검증 → 한 명이라도 READY 있으면 전체 거부 → 학생별 READY 행 + 공통 `group_order_no`. 같은 상품만 가능.
- PG에는 `group_order_no`로 **합계 금액 승인 1건**. DB는 학생 수만큼 payment/pass 행, **같은 tid 공유**.
- `confirmPaidGroup`이 전원을 한 트랜잭션으로 확정 (일부만 확정되는 상태 방지).

### 2-3. 구매 제한

- 결제창이 열린(READY) 주문이 있으면 새 주문을 만들지 않고 재사용(단건) / 거부(그룹).
- **PAID가 있어도 재구매 허용** — 12회를 다 쓰면 같은 달에도 다시 산다. 여러 장 보유 가능.

## 3. 이용권 발급 → 소모 과정

### 3-1. 발급

- 결제 승인 시 `pass` 1장: `source=PG`, `ref_no=order_no`, `total=remain=12`, `valid_from/valid_until=NULL`(미배정).
- 이용권이 결제를 가리키는 구조라, 결제 방식(PG/서당/무상)이 달라도 차감·복구 로직은 한 벌이다.

### 3-2. 예약 = 차감 (`ReservationService.reserveOne` → `PassService.consumeForReservation`)

1. 학생 행 `UPDLOCK` — 같은 학생 동시 요청 직렬화
2. 검증 — 이미 끝난 회차 거부 / 학생은 **회차 시작 24시간 전**까지만(직원 예외) / **하루 최대 4회차** / 슬롯 정원
3. reservation INSERT (`RESERVED`)
4. 회차 **날짜 기준**으로 쓸 이용권 선택 — 미회수 · 잔여>0 · (미배정 또는 그 날짜가 기간 안)
   정렬: 기간 정해진 것 → 먼저 만료되는 것 → 먼저 산 것 → **미배정은 맨 마지막**
5. 미배정이면 `activatePass`: `valid_from = 회차 날짜`, `valid_until = +89일` (90일)
6. `decrementRemain` + `pass_use` INSERT (`reservation_id`, `used_date=회차 날짜`)
7. 쓸 이용권이 없으면 예외 → **예약·정원 증가까지 전부 롤백** ("결제 후 예약해주세요")

### 3-3. 취소 = 복구 (`cancelInternal` → `restoreForReservation`)

- 학생: 회차 시작 24시간 전까지 / 직원: 당일도 가능 / RESERVED만 취소 가능
- `pass_use.canceled_at` 기록 → `remain +1` (remain<total, 미회수일 때만)
- 그 이용권의 살아있는 차감이 0건이 되면 **기간 해제**(다시 미배정) — 예약했다 바로 취소한 것만으로 90일이 시작되지 않게

### 3-4. 입실 · 노쇼

- 입실(`markAttended`): 오늘 예약 없으면 입실 불가, 회차 시작 10분 전~종료 사이만. 첫 입실 한 번으로 그날 RESERVED 전부 ATTENDED. **차감 없음.**
- 노쇼: 매일 배치로 RESERVED → NOSHOW. **복구 없음.**

### 3-5. 종료

| 상태 | 조건 | 비고 |
|---|---|---|
| 소진 | remain = 0 | 취소로 다시 살아날 수 있음 |
| 만료 | 오늘 > valid_until | 잔여 소멸(이월 없음). 별도 배치 없이 조회 조건에서 제외 |
| 회수 | revoked_at NOT NULL | 환불 시. 이후 예약 취소로도 복구 안 됨 |

- 잔여 표시(`sumRemain`) = 미회수 이용권 중 (미배정 + 오늘 유효)의 remain 합계
- 불변식: 살아있는 `pass_use` 건수 = `total_count − remain_count`

## 4. 환불

| 단계 | 내용 |
|---|---|
| 권한 | 결제 주인이 요청자의 **형제 그룹** 안이면 허용 |
| 선점 | `claimRefund` — `refund_requested_at` 원자적 UPDATE (동시 요청 이중 PG 취소 방지), finally에서 해제 |
| 조건 | PAID / 이전 환불 없음(**1회만**) / tid·paid_at 있음 / 이용권 미회수 / **결제일+3개월 이내** / 잔여>0 |
| 금액 | `min(잔여 × 3,000원, 결제금액 − 기환불액)` · rule_code `R2610_UNIT3000` (코드 상수, `refund_rule` 테이블은 안 읽음) |
| 기록 | PG 호출 전 `payment_cancel` REQ (rule_code, used_days, used_count 스냅샷) |
| 부분/전체 | 형제 묶음은 같은 tid라 **그룹 합계 기준**. 그룹 안에서 이미 환불이 있었으면 무조건 부분취소 |
| PG | `v2/pg/partialRefund` 또는 `v2/pg/refund` |
| 성공 | `payment_cancel` DONE, `refund_amount +=`(전액이면 CANCELED), **이용권 회수** — 한 트랜잭션 |
| 실패 | `payment_cancel` FAIL, 금액·이용권 변경 없음, 재시도 가능 |

예: 12회권 60,000원, 5회 사용 → 잔여 7 × 3,000 = **21,000원**. 최대 36,000원이므로 현 정책에서는 **전액환불(CANCELED)이 발생하지 않는다.**

## 5. 자동결제 (빌키 구독) — 잠김

- **카드 등록은 동작한다**: `/payment/billing/checkout` → subscription/member PENDING → INILite 빌키발급 창(price=0, 돈 안 빠짐) → `/payment/billing/return`에서 billkey 받아 ACTIVE. 앵커일·다음 청구일 = 학부모가 고른 첫 결제일(3개월 이내).
- **청구는 잠겨 있다**: `SubscriptionBillingJob.chargeDueSubscriptions`의 `@Scheduled` 주석 처리 + `MONTHLY_BILLING_ENABLED=false`.
  - 사유: 12회권·90일 정책에서 매월 12회 충전은 맞지 않음. 새 정책 "잔여 2회 남으면 자동결제" 트리거 미구현.
- 켜면 동작할 로직: 선점(`claimDue`) → 결정적 주문번호 `SUB{id}-{yyyyMMdd}` → `v2/pg/billing` 합산 승인 → 성공 시 멤버별 `confirmPaid`(PAID+이용권) / 거절 시 D+1·D+3·D+5 재시도 후 PAUSED / 응답 유실 시 거래조회.
- 결과적으로 지금 카드를 등록하면 **ACTIVE인데 청구도 이용권도 영원히 안 나오는** 상태가 된다. 앱에는 진입점이 없어 실사용자는 들어올 수 없다.
- 해지는 DB 상태만 바꾸고 **이니시스 빌키 삭제 호출은 없다.**

| 서당 병행 | 설계만 있음(SEODANG, 달력월), 발급 연동 없음 |

## 7. 현재 이슈 / 불일치 (변경 전 확인 필요)

1. **앱 환불 예상액 ≠ 실제 환불액** — `AppMapper.selectPassList`는 `amount/total×remain`(회당 5,000원), 실제 `calculateRefund`는 회당 3,000원. 7회 남으면 앱 35,000원 / 실제 21,000원.
2. **환불 후 미래 예약이 남는다** — 환불은 이용권만 회수하고 이미 잡힌 RESERVED 예약은 건드리지 않는다. 이후 그 예약을 취소해도 복구되지 않는다.
3. **자동결제 반쪽 상태** — 등록하면 ACTIVE지만 청구 없음 / 해지 시 빌키 삭제 없음 / `결제_정책_결정사항.csv`(재시도 없음·즉시 정지·빌키 삭제)와 코드(D+1/3/5 재시도·PAUSED·삭제 없음)가 다르다.
4. **서당·무상 이용권 발급 경로 없음** — `grantFromSeodang` 호출부가 없고, FREE 발급 API/화면도 없다.
5. **관리자 수기 결제·환불 없음** — 결제 내역 화면의 수기 등록은 "준비 중", 환불은 앱에서만.
6. **미사용 잔재** — `refund_rule` 테이블, `POST /payment/approve`(PC 인증), `completeCardReg`(옛 빌키 경로), `billing_ym`(구매월 라벨로만 사용).
7. **운영 설정** — `application-prod.yml`이 `test-mode: true`, return/close URL이 ngrok(2026-10-21 로컬 테스트 상태). 결제 이상 건 화면에 센터 구분 없음.
8. **모바일 승인 후 실패는 자동 취소 불가** — P_REQ_URL 승인에는 망취소가 없어 금액 불일치·확정 실패는 전부 상점관리자 수동 취소.

## 8. 결제 방식 변경 시 영향 범위

- **결제 시작 / 결제창**: `PaymentService.prepare/prepareGroup`, `PaymentCheckoutViewController`, `templates/payment/*`
- **승인 → 이용권 발급의 단일 합류 지점**: `PaymentTxService.confirmPaid → PassService.grantUnassigned` (일시불·형제·자동결제·배치 복구가 전부 여기로 모인다)

- **DB 유니크 방어선**: `UX_payment_active_cycle`(student, service, cycle_from — READY|PAID), `UX_subscription_member_active`(student, service — ACTIVE)
