# 예약 기능 구현 계획

- 작성일: 2026-08-18 (운영 스케줄 완료 직후, 착수 전)
- 범위: 학생 예약, 예약 현황 조회, 센터 대리 예약
- 선행: 운영 스케줄(`docs/운영스케줄_구현계획.md`) — slot_instance를 찍는 쪽은 완성됨

## 지금 상태 한 줄 요약

**운영 스케줄이 만든 `slot_instance`를 쓰는 코드가 아직 하나도 없다.** 예약은 여전히 옛 테이블에서
1~4교시 고정으로 돌아가고 있고, 두 체계가 DB에 동시에 존재한다.

## 자산 정리

### 신규 (운영 스케줄에서 만든 것 — 소비자 0)

| 테이블 | 내용 |
|---|---|
| `erp_bookstore_slot_instance` | 날짜 x 회차로 확정된 슬롯. `capacity`, `reserved_count`, `status(OPEN/CLOSED)` 보유 |
| `erp_bookstore_reservation` | 예약 현재 상태 (RESERVED/CANCELED/ATTENDED/NOSHOW) |
| `erp_bookstore_reservation_log` | 상태 전환 전체 이력 (`changed_by`, `changed_by_role`) — append-only |

- 동일 회차 중복 예약은 필터링된 유니크 인덱스(`UX_reservation_slot_student`, status='RESERVED')로 DB가 막는다.
- `CK_slot_instance_count`가 `reserved_count <= capacity`를 보장한다.

### 기존 (돌아가고 있는 것)

| 위치 | 내용 |
|---|---|
| `erp_bookstore_clinic_reservation` | student_id + reservation_date + time_slot('1'~'4') |
| `reservation` 패키지 | `/admin/monitor/reservation` — list / students / register / delete |
| `templates/reservation/reservation.html` | 센터 직원이 학생 예약을 대신 잡는 화면 |
| `MonitorMapper` | **예약을 루트로** 카드 목록 조회 (미입실 판단이 예약 기준) |
| `DiaryMapper` | 예약을 루트로 성장일지 조회 |
| `monitor-live.js` / `reservation.js` / `diary.js` | `TIME_SLOTS` 상수가 **세 파일에 복사돼 있음** (1~4교시, 시각 하드코딩) |

## 착수 전 결정 4가지

### ① 구·신 테이블을 통합할 것인가 (가장 중요)

통합하면 운영 스케줄이 실제로 쓰이기 시작하고 회차가 데이터로 관리된다. 대신 모니터링·성장일지의
조회 루트를 함께 바꿔야 한다. 병행하면 빠르지만 같은 학생의 예약이 두 테이블로 갈리고 모니터링에는
한쪽만 보인다 — 9/30 전에 결국 통합해야 한다.

**지금이 가장 싼 시점이다.** 신규 테이블에 데이터가 없어 이관할 것이 없고, 예약 API를 어차피 새로 쓴다.

### ② 예약 주체 — 학생 / 센터 / 둘 다

학생 본인 예약 화면은 현재 존재하지 않는다. 센터 대리 예약은 이미 있다(옛 테이블 기반).
`reservation_log.changed_by_role`이 STUDENT/PARENT/ADMIN/SYSTEM을 구분하도록 설계돼 있으므로
주체가 늘어도 스키마는 그대로 간다.

### ③ 취소 규칙 — 누가, 언제까지

당일 취소 허용 여부, 시작 n시간 전까지 등. `reservation.canceled_at` / `cancel_reason` 컬럼은 이미 있다.
휴무 예외를 등록하면 그날 예약을 관리자가 일괄 취소해야 하는데, 그 경로도 여기서 같이 정한다.

### ④ 같은 날 여러 회차 예약 허용 여부

DB는 "같은 회차 중복"만 막고 있다. 하루 2회차 이상 예약은 응용 계층에서 판단해야 한다.

## 작업 순서 초안 (①=통합 기준)

1. **예약 도메인 기초** — 슬롯 조회 / 예약 생성 / 취소.
   - 정원 동시성: `reserved_count` 증가는 `UPDATE ... WHERE reserved_count < capacity` 조건부 갱신으로
     처리하고 영향 행 수가 0이면 마감으로 응답한다(SELECT 후 INSERT는 경합에서 뚫린다).
   - 모든 상태 전환에 `reservation_log` 기록. 취소 주체 분쟁 방지가 이 테이블의 존재 이유다.
2. **센터 대리 예약** — 기존 `/admin/monitor/reservation`을 신규 기반으로 교체.
   화면은 4교시 고정 UI라 회차 수 가변 대응이 필요하다.
3. **예약 현황 조회** — 날짜별 슬롯 x 예약자, 정원 대비 현황.
4. **모니터링·성장일지 이관** — `MonitorMapper`/`DiaryMapper` 조회 루트 교체, `TIME_SLOTS` 하드코딩 3곳 제거.
5. **학생 본인 예약** — 학생 앱에서 날짜·회차 선택.

## 미리 알아둘 제약

- **예약이 걸린 날짜는 스케줄을 못 바꾼다**(결정 4). 반대로 스케줄을 자주 바꾸는 초기 운영에서는
  예약이 있는 것만으로 저장이 막히므로, 관리자에게 어떻게 안내할지 정해야 한다.
- **예약 오픈 기간은 28일**(`ScheduleMaterializer.RESERVATION_OPEN_DAYS`) — 임의값이라 확정 필요.
  월 단위 운영이면 45~60일 또는 "다음 달 말일까지" 방식이 나을 수 있다.
- `slot_instance.status = 'CLOSED'`인 회차(예외로 마감된 회차)는 예약을 받지 않는다.
- 시간은 전부 KST. SQL에서 `GETDATE()` 금지, `DATEADD(HOUR, 9, GETUTCDATE())`를 쓴다.
- 운영 DB에 `db/patch-schedule_exception_slot-time.sql` 미적용 상태 — 배포 전 실행해야 한다.
